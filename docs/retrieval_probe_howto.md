# 검색이 제대로 되는지 확인하는 법

질문을 넣었을 때 **맞는 청크가 나오는지** 보는 도구는 두 개다. 목적이 다르다.

| 도구 | 무엇을 보나 | 검색기 | GPU | 걸리는 시간 |
|---|---|---|---|---|
| `eval/probe_benchmark.py` | 골든셋 42문항을 한꺼번에 채점 — **몇 건 맞혔나** | BM25만 | 불필요 | 11초 |
| `eval/show_chunks.py` | 질문 하나에 **어떤 청크가 나왔나** (본문 그대로) | 하이브리드 (BM25+dense RRF) | 필요 | 로드 34초 + 질의당 0.2초 |

둘 다 리포 루트에서 실행한다.

---

## 1. 집계로 보기 — `eval/probe_benchmark.py`

```powershell
python eval\probe_benchmark.py --k 20
python eval\probe_benchmark.py --k 20 --scenario multi_closed
```

인자는 두 개뿐이다.

- `--scenario` — `search_closed`(기본) `search_open` `multi_closed` `multi_open` `complex_closed` `complex_open`.
  골든셋이 43개 파일 × 6유형이라 유형당 42건씩 돈다.
- `--k` — 상위 몇 건 안에 들면 적중으로 칠지. 기본 20.

### 출력 읽는 법

행 하나가 질문 하나다.

- **후보행** — 그 회사 × `is_latest` 로 좁힌 뒤 남은 청크 수. 이 안에서만 점수를 낸다.
- **정답청크** — `ground_truth` 에서 뽑은 **앞 3개 숫자**를 실제로 담고 있는 청크 수.
- **HIT / MISS / n/a** — `n/a` 는 검색 실패가 아니라 **대조할 숫자를 못 뽑은 것**이다.

> **주의 — 지표에 구멍이 있다.** 정답 숫자를 뽑는 정규식이 `\d{1,3}(?:,\d{3})+` 이라
> **천 단위 콤마가 있는 숫자만** 잡는다. `0.98 USD`, `13명(19%)`, `16개국·40개 대리점` 같은
> 작은 값은 통째로 빠진다. `search_closed` 의 `n/a` 3건(LG에너지솔루션·두산로보틱스·레인보우로보틱스)이
> 전부 이 경우다 — 청킹이 깨진 게 아니다. 즉 `정답 숫자가 코퍼스에 존재 39/42` 는
> **상한이 아니라 "콤마 있는 숫자로 채점 가능한 문항 수"** 로 읽어야 한다.

맨 아래 세 줄이 요약이다. 스크립트는 `정답 숫자가 코퍼스에 존재` 를 상한으로 삼아
`top-k 안에 정답 청크` 를 그 값으로 나눈 비율을 찍지만, 위 구멍 때문에 그 분모는 실제 상한보다 작다.
비율보다 **`top-k 안에 정답 청크 / 전체 42건`** 을 보는 편이 안전하다.

## 2. 본문으로 보기 — `eval/show_chunks.py`

```powershell
# 골든셋 문항 — 질문·정답·검색된 청크를 한 화면에서 대조
python eval\show_chunks.py --case 삼성전자 --scenario search_closed

# 아무 질문이나
python eval\show_chunks.py "연구개발비용 총계" --company 삼성전자 --fy 2025 -k 5

# 대화형 — 모델 로드 34초를 한 번만 치른다. 여러 개 볼 거면 이걸 쓴다
python eval\show_chunks.py
```

인자

| 인자 | 뜻 |
|---|---|
| `--company` | 회사명. 별칭 사전(`config/aliases.yaml`)으로 해석한다 |
| `--fy` | **사업연도**. 접수연도가 아니다 — 2024 사업연도 사업보고서는 2025년에 접수된다 |
| `--group` | 문서군 (`periodic` / `major` / `exchange` …) |
| `-k` | 상위 몇 건을 볼지 (기본 5) |
| `--chars` | 본문 표시 글자수 (기본 600). `0` 이면 전체 |
| `--case` | 골든셋 회사명. 그 회사 문항을 질문 대신 쓰고 정답과 대조한다 |
| `--scenario` | `--case` 와 함께. 기본 `search_closed` |
| `--cpu` | GPU 없이. 느리다 |

대화형 지시어

```
/company 삼성전자   회사 필터        /company        해제
/fy 2025           사업연도 필터     /fy             해제
/group periodic    문서군 필터       /group          해제
/k 8               상위 몇 건        /chars 0        본문 전체
/case 삼성전자 search_closed        골든셋 문항 불러서 정답과 대조
/companies         골든셋에 있는 회사 목록        /q  종료
```

### 출력 읽는 법

```
--- 1. rrf 0.03279  bm25 106.62  dense 0.648  [문서O · 정답숫자 6/6]
    삼성전자 · 사업보고서 (2025.12) · 접수 20260310 (20260310002820)
    [삼성전자] 사업보고서 (2025.12) > II. 사업의 내용 > 6. 주요계약 및 연구개발활동
      | 연구개발비용 총계 | 37,754,815 | 35,021,531 | 28,352,769 |
      … (총 1,151자, 전체는 --chars 0)
```

- `rrf` 가 실제 정렬 기준이다. `bm25` 와 `dense` 는 참고용 — 둘 중 어느 쪽이 이 청크를 올렸는지 본다.
- `--case` 일 때만 대괄호 표시가 붙는다.
  **문서O/X** 는 그 청크의 접수번호가 골든셋 `doc_info` 의 정답 문서에 드는지,
  **정답숫자 n/m** 은 `ground_truth` 의 숫자가 본문에 몇 개 들어 있는지다.
- 헤더의 `후보 N행 -> pool M건` 은 하드필터로 좁힌 뒤 융합·중복제거를 거쳐 남은 수다.
  `정정 전 첨부 k건 버림` 은 같은 계열 최신본이 더 위에 이미 뽑혀서 버린 청크 수다(단계 0.7 규칙).

## 골든셋에 이미 들어 있는 정답 라벨

따로 라벨링할 필요가 없다. `Question/질문_(수정해서 다시 할 것)/benchmark_*AR.json` 에서

- `doc_info` 안의 **14자리 접수번호** = 정답 문서 (43개 파일 전부에 있다, 결측 0건)
- 파일명 `benchmark_삼성전자_2025AR.json` 의 `2025AR` = **사업연도**
- `ground_truth` 안의 숫자 = 근거 청크 본문에 그대로 있어야 하는 값

이 셋으로 **문서 단위 recall@k** 를 자동 채점할 수 있다. 청크 단위 정답은 없지만,
`src/eval/questions.jsonl` 의 약한 기대치(`expect_any`)보다 훨씬 단단하다.

## 지금까지 측정한 수치 (2026-08-31)

골든셋 표본 36문항, top-5, 문서 단위 적중:

| 필터 | doc@1 | doc@5 |
|---|---|---|
| 없음 | 0.14 | 0.36 |
| 회사만 | 0.19 | 0.58 |
| 회사 + 사업연도 | **0.61** | **0.89** |

`eval/probe_benchmark.py` 유형별 (BM25만, top-20):

| 시나리오 | 정답 숫자가 코퍼스에 존재 | top-20 적중 |
|---|---|---|
| `search_closed` | 39/42 | 34/42 |
| `complex_closed` | 34/42 | 32/42 |
| `multi_closed` | 42/42 | 31/42 |
| `search_open` | 38/42 | 10/42 |

읽는 법

- 틀리는 이유는 대부분 **회사·섹션은 맞는데 보고서 판이 틀린 것**이다.
  같은 섹션이 분기·반기·사업보고서에 반복되니 본문만으로는 구분이 안 된다.
  `--fy` 를 주면 doc@5 가 0.58 → 0.89 로 뛴다.
- `search_open`(서술형)이 낮은 건 질의에 고유 용어가 없어 BM25 혼자로는 못 잡기 때문이다. dense 몫이다.
- 이 표의 `정답 숫자가 코퍼스에 존재` 열은 위에 적은 정규식 구멍 때문에 **상한이 아니다**. 참고치로만 본다.

## 주의

- `src/eval/ask.py` 의 대화형 CLI는 **다른 검색기**(`src.eval.retriever`, dense + bge sparse 가중합)를 쓴다.
  하이브리드(BM25 + RRF)가 아니다. 섞어서 비교하지 말 것. 자세한 건 `docs/retrieval_eval_notes.md`.
- `eval/probe_benchmark.py` 는 BM25만 보므로 그 수치는 **하이브리드의 하한**이다.
- 파이프로 한글을 넣으면 cp949 로 읽혀 깨진다. `show_chunks.py` 는 stdin 을 utf-8 로 고정해뒀다.
  콘솔 직접 입력에는 영향이 없다.
