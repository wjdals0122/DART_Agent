## 단계 0 — 파일이 실제로 뭐가 있는지 확인 + 임베딩 건강검진 (2026-08-30)

### 왜 했나
계획서는 특정 파일들이 특정 위치에 있다고 가정하고 쓰여 있었다.
그 가정이 맞는지 먼저 눈으로 확인하지 않으면, 나중에 없는 필드를 참조하는 코드를 잔뜩 짜게 된다.

### 무엇을 알아냈나

**(1) 계획서가 가정한 경로 중 상당수가 실제와 달랐다.**

| 계획서가 있다고 한 것 | 실제 |
|---|---|
| `data/raw/universe.csv` (회사 목록) | 없음. `corpus/universe.csv` 에 있음 |
| `data/raw/manifest.jsonl` (문서 목록) | 없음. `corpus/manifest.jsonl` 에 있음 |
| `data/processed/corpus.db` (재무 수치 DB) | **아예 없음.** 리포 전체에 데이터베이스 파일이 0개 |
| `docs/plan/` 안의 설계문서 6개 | 없음 |
| `CLAUDE.md` (프로젝트 상시 규칙) | 리포 루트에 없었음 (`prompt/Claude.me` 에 내용만 있었음) |

**(2) 가장 중요한 발견 — 청크 파일이 두 벌 있고, 그중 한 벌만 진짜다.**

- `data/processed/chunks.jsonl.gz` : 129만 417조각. 이 리포의 자체 청킹 스크립트가 만든 것.
- `data/processed/chunks_by_10_companies/` 안의 파일 8개 : 합쳐서 61만 4,578조각.

**임베딩(숫자 변환)은 두 번째 것으로만 했다.** 첫 번째 파일은 임베딩 결과와 아무 관계가 없다.
앞으로 만드는 검색기는 전부 두 번째를 봐야 한다. 첫 번째를 잘못 참조하면 조각 번호가 통째로 어긋난다.

**(3) 필드 이름이 계획서와 다르다.** 계획서는 `embed_text`, `corp_name`, `doc_group` 같은 이름을 쓰라고 했는데
실제 파일은 다른 이름을 쓰고 있었다.

| 계획서의 이름 | 실제 이름 | 뜻 |
|---|---|---|
| `embed_text` | `embedding_text` | 임베딩할 때 실제로 넣은 글 |
| `text` | `content` | 사람에게 보여줄 본문 |
| `corp_name` | `company` | 회사 이름 |
| `corp_code` | `stock_code` | 종목코드(6자리) |
| `doc_group` | `disclosure_type` | 공시 종류 |
| `rcept_no` | `receipt_no` | 접수번호 |

**(4) 아주 위험한 함정 하나 — 같은 이름, 다른 값.**

`id_map.parquet`(조각 번호 ↔ 문서 정보 대응표) 에 `corp_code` 라는 칸이 있는데,
여기 들어 있는 값은 **6자리 종목코드**(`097950`) 다.
그런데 `universe.csv` 와 `manifest.jsonl` 의 `corp_code` 는 **8자리 금감원 고유번호**(`00126380`) 다.

이름이 같아서 무심코 섞어 쓰면 회사 필터가 **항상 0건**이 되는데,
에러도 경고도 안 나고 그냥 "검색 결과 없음"으로 조용히 지나간다. 원인 찾기가 매우 어렵다.

**(5) 다행인 것들**

- 조각 수 61만 4,578개가 임베딩 결과·대응표와 **정확히 일치**. 하나도 안 어긋남.
- 회사코드·공시종류가 **비어 있는 조각이 0건**.
- `base_year`(사업연도) 가 정수형(2024)이다. 이게 실수형(2024.0)이었으면 연도 필터가 조용히 전부 실패했을 것이다.
- 조각의 `receipt_no` 가 문서목록의 `rcept_no` 와 **4,204개 전부 연결**된다. 문서 제목·정정 여부를 붙일 수 있다.

### 임베딩 건강검진

계획서가 지목한 검사 스크립트가 리포에 없어서 같은 목적으로 새로 만들었다.

- 만든 파일: **`eval/embed_health_check.py`**
  - 하는 일: 조각 200개를 무작위로 골라 **다시 숫자로 바꾼 뒤**, 원래 저장돼 있던 숫자와
    가장 닮은 조각이 자기 자신인지 확인한다. 자기 자신이 1등으로 안 나오면 어딘가에서
    조각과 숫자의 짝이 어긋났다는 뜻이다.

결과: **200개 전부 자기 자신이 1등.** (정확히 자기 자신 178개 + 글자가 완전히 똑같은 중복 조각이 1등 22개)
자기 자신과의 유사도도 최소 0.9993 으로 사실상 1.0. 이상 없음.

- 보고서: `reports/embed_health.md`

## 단계 0.5 — "지켜야 할 약속" 확정 (2026-08-30)

### 왜 했나
검색기를 만들기 전에 못 박아둬야 할 게 세 가지 있었다.
(1) 조각의 순서를 어떻게 재현하나 (2) "옛날 버전" 표시가 정확한가 (3) 재무제표 조각이 어떻게 생겼나.

### (1) 조각 순서를 재현하는 코드를 만들었다

**문제:** 임베딩 결과는 그냥 숫자 61만 줄이다. 몇 번째 줄이 어느 조각인지는 **순서**로만 안다.
그 순서가 한 칸이라도 밀리면 검색 결과가 전부 엉뚱한 문서를 가리키게 된다.

**만든 파일: `src/search/source.py`**
- `iter_chunks_canonical()` — 원본 조각을 임베딩 때와 **똑같은 순서로** 하나씩 꺼내주는 함수.
- 순서의 근거를 파일이름 정렬이 아니라 `meta.json` 에 기록된 파일 목록으로 잡았다.
  파일이름 정렬은 운영체제나 설정에 따라 달라질 수 있지만, 기록은 안 변한다.

**검증 결과: 61만 4,578줄 전부 일치. 어긋난 줄 0개.** (16초)
글자를 지문처럼 압축한 값(sha1)을 줄마다 대조해서 확인했다.

### (2) "옛날 버전" 표시가 부정확하다는 걸 발견했다 — 이게 이 단계의 핵심

**배경:** 회사가 보고서를 냈다가 틀린 걸 발견하면 `[기재정정]사업보고서` 를 다시 낸다.
그러면 같은 내용의 보고서가 두 벌 있게 되고, 검색할 때 **옛날 버전이 걸리면 틀린 숫자를 답하게 된다.**

기존 코드에 `superseded`(밀려남) 라는 표시가 1만 4,442줄에 붙어 있었다. 이걸 그대로 쓰면 될 줄 알았다.

**확인해보니 이 표시는 전체의 일부만 잡고 있었다.**

기존 표시를 만드는 규칙은 "회사 + 보고서 제목이 같은데 접수번호가 여러 개면, 제일 큰 것 빼고 옛날 것"이었다.
그런데 원본 제목은 `사업보고서 (2024.12)`, 정정본 제목은 `[기재정정]사업보고서 (2024.12)` 로 **제목이 다르다.**
그래서 원본과 정정본이 아예 같은 묶음으로 들어가지 않았다.

결과적으로 이 표시가 잡은 건 **"정정본이 또 정정된"** 경우뿐이었다.

```
정기보고서 중 최신이 아닌 줄 : 12만 3,739줄
  기존 표시가 잡은 것        :  1만 4,442줄
  못 잡고 남은 것            : 10만 9,297줄   ← 옛날 숫자가 그대로 검색됨
```

실제 사례:
```
CJ제일제당 사업보고서(2024.12)
  20250317000648  원본     1,085줄   ← 옛날 것인데 표시 없음
  20250321001604  정정본     867줄
```

**그리고 반대 방향의 함정도 같이 확인했다.**
원래 계획서에는 "정정공시는 기본 제외"라고 적혀 있었는데, 문서목록의 `is_correction`(정정여부) 로
그대로 걸러내면 **정확히 거꾸로 작동한다.** 정정본이 최신이자 옳은 버전이기 때문이다.
정정본을 빼면 틀린 숫자를 답하게 된다.

이 두 가지를 보고하고 멈췄다. (판단은 사람이 하기로 한 사항)

### (3) 재무제표 조각이 어떻게 생겼는지 확인했다

`section_path`(문서 안에서의 위치) 에 재무제표 관련 말이 들어간 조각이 29만 7,836줄 (전체의 48%).
다만 이건 "재무제표 주석", "재무제표 작성기준" 같은 것까지 다 센 수치라 부풀려져 있다.
진짜 표(재무상태표·손익계산서·현금흐름표·자본변동표)만 세면 3만 7천 줄 수준.

**실제 조각 모양 (CJ제일제당 분기보고서 2023.03):**
```
위치: III. 재무에 관한 사항 > 2. 연결재무제표 > (단위 : 천원)
내용: | 구분 | 제 17 기 1분기말 | 제 16 기말 |
      | 유동자산 | 9,917,079,269 | 9,759,274,570 |
      | 현금및현금성자산 | 1,937,702,073 | 1,797,257,804 |
```

여기서 중요한 점 세 가지:
- **단위(천원)는 위치 정보 맨 끝에 있다.** 본문 안에는 없다.
- **기수(제 17 기)는 본문 표의 머리행에 있다.** 표가 여러 조각으로 잘려도 머리행은 조각마다 다시 붙어 있다. 다행.
- **달력 연도(2023년)는 어디에도 안 적혀 있다.** "제 17 기"가 몇 년인지는 문서의 사업연도 정보로 따로 환산해야 한다.

## 단계 0.7 — 옛날 버전을 걸러내는 표 만들기 (2026-08-30)

### 왜 했나
단계 0.5에서 "기존 표시로는 옛날 버전을 다 못 거른다"는 걸 확인했다.
그래서 제대로 된 걸러내기 표를 새로 만들기로 했다.

### 어떤 방식을 골랐나

선택지가 셋 있었는데 (c′) 로 결정됐다.

- (a) 기존 표시 그대로 쓰기 → 10만 9천 줄이 안 걸러짐. 부족.
- (b) 옛날 접수번호는 통째로 빼기 → 확실하지만 **정정본에 안 들어간 내용까지 같이 사라진다.**
- **(c′) 옛날 것을 빼되, 정정본에 같은 위치의 내용이 아예 없으면 그건 남긴다.** ← 이걸로 결정

(b)가 위험한 이유가 실제 데이터로 확인됐다. 정정본은 본문은 다시 내면서
**감사받은 재무제표 첨부·감사보고서를 통째로 빼고 내는 경우가 많다.**

```
CJ제일제당 원본  20250317000648 : (첨부)연결재무제표 144줄, (첨부)재무제표 96줄, 감사보고서 8줄
CJ제일제당 정정본 20250321001604 : 위 항목 전부 0줄 (대신 "정정신고" 52줄이 추가)
```
(b)로 했으면 CJ제일제당의 2024년 감사받은 재무제표가 코퍼스에서 통째로 사라졌을 것이다.

### 만든 것

**`src/search/build_latest_mask.py`** → 결과물 `data/index/latest_mask.npz`

하는 일을 말로 풀면:
1. 정기보고서만 대상으로, `회사 + (제목에서 [기재정정] 떼어낸 것)` 으로 같은 보고서끼리 묶는다.
   - 사업보고서·분기보고서 같은 정기보고서만 묶는다. 계약체결 공시 같은 건 제목이 같아도 매번 다른 사건이라 묶으면 안 된다.
2. 묶음 안에서 접수번호가 제일 큰 것 = 최신본. 나머지 = 옛날 것.
3. 옛날 것의 각 줄에 대해, **문서 안에서의 위치가 최신본에도 있으면 → 제외**,
   최신본에는 아예 없는 위치면 → **남긴다**.
4. `is_latest`(쓸 것인가) 와 `preserved`(옛날 것인데 살려둔 것인가) 두 개의 참·거짓 목록을 파일로 저장.

`data/index/vectors/` 는 손대면 안 되는 폴더라 그 밖(`data/index/`)에 저장했다.

### 결과

| 항목 | 값 | 뜻 |
|---|---|---|
| 정기보고서 묶음 | 897개 (그중 정정된 것 135개) | |
| 옛날 것 총 줄 수 | 12만 3,739줄 | |
| **제외한 줄** | **9만 7,223줄** | 최신본에 같은 자리 내용이 있어서 뺌 |
| **살려둔 줄** | **2만 6,516줄** | 정정본에 없는 첨부·감사보고서 |
| **검색 대상으로 남은 줄** | **51만 7,355줄** / 61만 4,578줄 | |
| 소요 시간 | 19.2초 | |

**살려둔 게 뭔지 확인** (CJ제일제당 원본 1,085줄 중 277줄이 살아남음):
```
127줄  (첨부)연결재무제표 > 주석 > CJ제일제당주식회사와 그 종속기업
 84줄  (첨부)재무제표 > 주석 > CJ제일제당주식회사
  6줄  독립된 감사인의 감사보고서
  4줄  외부감사 실시내용 > 주요 감사실시내용
  ...
```
의도한 대로 **정정본이 빼먹은 첨부 재무제표와 감사보고서만** 살아남았다. 규칙이 제대로 동작한다.

HD현대일렉트릭도 같은 모양 (772줄 중 308줄 보존, 전부 첨부·감사 관련).

### 남는 위험 (사람 판단 필요)

살려둔 첨부 재무제표는 **정정하기 전 숫자**다.
만약 정정이 재무 수치를 고친 것이었다면, 본문(최신)과 첨부(옛날)가 서로 다른 값을 들고
동시에 검색될 수 있다. 정정본에 첨부가 아예 없으니 이 방식으로는 피할 수 없는 한계다.

대응 방법 세 가지 중 하나를 골라야 한다:
1. 그냥 동등하게 취급 (현재)
2. 살려둔 줄은 검색 순위를 뒤로 미루기
3. "이건 정정 전 첨부입니다" 라는 표시를 붙여서 보여주기

## 단계 0.7-보완 — 결정 추록 v2 반영 (2026-08-30)

### 왜 했나
단계 0.7의 규칙이 정본으로 확정됐고, 살려둔 2만 6,516줄(정정 전 첨부 재무제표)의
취급 방법도 정해졌다. 그 방법을 쓰려면 걸러내기 표에 정보가 하나 더 필요해서 추가했다.

### 정해진 취급 방법 — "조건부 버리기"

살려둔 줄을 항상 쓰지도, 항상 뒤로 미루지도 않는다. **문제가 실제로 생길 때만 버린다.**

값이 어긋날 수 있는 상황은 딱 하나다 — **같은 보고서의 최신본과 옛날 첨부가 검색 결과에 같이 뜰 때.**
그래서 이렇게 한다:

> 검색 결과를 조립할 때, 같은 보고서 묶음의 **최신본 조각이 이미 뽑혀 있으면**
> 그 묶음의 살려둔(옛날) 조각은 버린다. 최신본 조각이 하나도 안 뽑혔을 때만 남긴다.

실제로 어떻게 되냐면:

| 질문 | 무슨 일이 일어나나 |
|---|---|
| "CJ제일제당 2024년 매출액" | 본문 III장(최신)이 뽑힘 → 같은 묶음의 옛날 첨부 재무제표는 버려짐. **숫자가 어긋날 일이 없다** |
| "CJ제일제당 감사의견" | 최신본에는 감사보고서가 아예 없음 → 아무것도 안 버려짐. **옛날 감사보고서가 그대로 살아남는다** |

좋은 점은 "옛날 것은 점수를 30% 깎는다" 같은 **사람이 정한 임의의 숫자가 하나도 안 들어간다**는 것이다.
버릴지 말지가 데이터만 보고 결정된다.

### 무엇을 고쳤나

**`src/search/build_latest_mask.py`** 에 세 가지 추가:

1. **`series_code`(보고서 묶음 번호)를 결과 파일에 같이 저장.**
   위의 "같은 묶음의 최신본이 이미 뽑혔나"를 판정하려면 조각마다 어느 묶음 소속인지 알아야 한다.
   숫자 하나로 표현해서 저장했다 (0~1,401번, 총 1,402개 묶음).
   정기보고서가 아닌 조각에도 번호를 준다 — 그쪽엔 살려둔 조각이 없어서 영향이 없고,
   대신 "번호 없음" 같은 예외값을 안 만들어도 돼서 쓰는 쪽 코드가 단순해진다.

2. **자동 회귀 검사 두 줄 추가.** 나중에 규칙을 손댔을 때 조용히 망가지는 걸 막는다.
   - 제외한 줄 수가 옛날 줄 총량(12만 3,739)에 도달하면 → 중단.
     그건 "옛날 것은 무조건 다 버린다"로 퇴화했다는 뜻이다.
   - 검색 대상 줄 수가 (전체 - 제외) 와 다르면 → 중단.
   - (기존에 있던 "살려둔 줄이 0이면 중단"과 합쳐 총 3개)

3. 파일 저장을 압축 방식으로 바꿈.

### 확인한 것

다시 돌린 결과는 이전과 동일하다 (숫자가 안 바뀌어야 정상이다).

```
정기보고서 묶음      897개 (정정된 것 135개)
옛날 줄 총량      12만 3,739줄
제외한 줄          9만 7,223줄
살려둔 줄          2만 6,516줄
검색 대상          51만 7,355줄
보고서 묶음 번호      1,402개
소요                 20.5초
```

새로 넣은 묶음 번호가 제대로 붙었는지 따로 검사했다:
- 번호에 음수(=오류값) 없음
- **살려둔 조각이 속한 81개 묶음 전부에 최신본 조각이 존재함** — 이게 성립해야
  "최신본이 뽑혔으면 버린다" 규칙이 작동한다
- 살려둔 조각은 45개 회사, 전부 정기보고서 소속
- 살려둔 조각은 "검색 대상"으로는 켜져 있음 — 버리는 판단은 검색할 때 하고, 표에서는 안 버린다

### 이번에 바로잡은 위험 하나

원래 설계문서의 코드는 조각의 위치를 비교할 때 **문서 제목까지 포함해서** 비교하게 돼 있었다.
그런데 제목이 `사업보고서 (2024.12)` 와 `[기재정정]사업보고서 (2024.12)` 로 서로 다르기 때문에
**모든 옛날 조각이 "최신본에 없는 내용"으로 판정돼 하나도 안 걸러졌을 것이다.**

더 나쁜 건, "살려둔 줄이 0이면 중단" 검사는 이 경우 통과해버린다는 점이다
(0이 아니라 12만 3,739 전부가 살아남으므로). 그래서 오류가 안 잡힌 채로 지나갔을 것이다.

단계 0.7에서 문서 제목을 떼고 비교하도록 만든 게 결과적으로 필수 수정이었다.

### 아직 안 한 것 (다음 단계에서 할 일로 기록)

"조건부 버리기"는 표만으로는 완성되지 않는다. 검색기(1-C)를 만들 때 아래를 넣어야 한다.

- **버리는 순서가 중요하다.** 문서당 개수 제한과 중복 제거를 **다 끝낸 뒤**,
  최종 개수(top_k)로 자르기 **직전**에 버려야 한다.
  먼저 잘라버리면 버린 자리가 안 채워져서 결과 개수가 모자라게 된다.
- 살려둔 조각이 최종 결과에 남으면 출처에 표시를 붙인다:
  `※ 자동 주석(공시 원문이 아님): 정정 전 첨부본(접수 2025-03-17). 이후 정정본이 존재하나 이 섹션은 정정본에 없음`
- 시스템 프롬프트에 한 줄 추가: 정정 전 자료의 숫자를 인용할 땐 정정 전임을 답변에 밝힐 것.

## 단계 1-A — 회사 이름 알아듣기 + 문장 쪼개기 (2026-08-30)

### 왜 했나
검색을 하려면 두 가지가 먼저 있어야 한다.
1. 사람이 "현대차" 라고 쳐도 **어느 회사인지 알아내는 것**
2. 문장을 **검색용 낱말로 쪼개는 것** (BM25 방식이 낱말 단위로 세기 때문에)

### 먼저 한 것 — kiwipiepy 설치

한국어 낱말 쪼개기 도구다. 계획서에 사람이 설치하기로 돼 있었는데 안 돼 있어서 제가 설치했다.
(`kiwipiepy 0.23.2`)

### (1) 회사 이름 알아듣기 — `src/search/aliases.py`

**별칭 사전을 데이터에서 긁어모았다: `config/aliases.yaml`**

조각마다 `aliases` 라는 칸에 그 회사의 다른 이름들이 이미 들어 있었다.
61만 조각을 전부 훑어 회사별로 모으고, `universe.csv` 의 정식명·상장명·영문명과 합쳤다.
**없는 별칭을 지어내지 않았다.** 데이터에 있는 것만 담았다. 70개사 · 별칭 429개.

예시:
```
SK하이닉스 : (주)SK하이닉스 / SK하이닉스 / SK하이닉스주식회사 / sk하이닉스 /
             에스케이하이닉스(주) / 에스케이하이닉스주식회사
JYP Ent   : (주)JYP Ent / (주)제이와이피엔터테인먼트 / JYP Ent / JYP Ent. /
             JYP Ent주식회사 / 제이와이피엔터테인먼트 / 주식회사제이와이피엔터테인먼트
```

**이름을 비교하기 전에 표준형으로 바꾼다.**
`(주)`, `주식회사`, `㈜` 같은 법인격 표기와 띄어쓰기·괄호·마침표를 지우고 소문자로 만든다.
그래서 `(주)삼성전자` `삼성전자주식회사` `삼성 전자` 가 전부 같은 것으로 취급된다.

여기서 함정이 하나 있었다. 영문 이름의 `Inc.` 를 안 지우면
`Alteogen Inc.` 안에 **`nc` 라는 글자가 들어 있어서** 회사명이 진짜 `NC` 인 엔씨소프트를
찾을 때 알테오젠까지 후보로 딸려 나온다. 그래서 영문 법인격(`Inc`, `Ltd`, `Corp` 등)은
**낱말 단위로** 떼어냈다. 통째로 문자열 치환하면 회사 이름 자체가 깎이기 때문이다.

**찾는 순서는 세 단계다.**
1. **완전히 같은 이름**이 있으면 그것만 본다 (`KT` → 케이티)
2. 없으면 **질의가 별칭 안에 들어 있는 것**을 찾는다 (`하이닉스` ⊂ `SK하이닉스`)
3. 그래도 없으면 **별칭이 질의 안에 들어 있는 것**을 찾는다 (`삼성전자 반도체` → 삼성전자)

각 단계에서 후보가 **딱 하나면 확정, 둘 이상이면 "모르겠다"** 로 답한다.
**절대 찍어서 하나를 고르지 않는다.** `SK` 처럼 애매하면 후보 목록을 그대로 돌려준다.

**돌려주는 것:** 8자리 금감원 번호(`corp_code`)와 6자리 종목코드(`stock_code`) **둘 다**.
단계 0에서 발견한 "같은 이름 다른 값" 함정 때문이다. 검색 필터에는 6자리만 쓴다.

### (2) 문장 쪼개기 — `src/search/tokenize_ko.py`

`LIG넥스원의 2024년 유형자산 취득액은 3,908,761백만원이다`
→ `['lig넥스원', '2024', '년', '유형', '자산', '취득', '액', '3,908,761', '백만', '원', '3908761']`

신경 쓴 것 네 가지:

1. **회사 이름이 쪼개지면 안 된다.** 그냥 두면 `LIG넥스원` 이 `LIG` + `넥스` + `원` 으로
   갈라진다. 그래서 별칭 547개를 전부 "이건 고유명사다" 라고 도구에 미리 등록했다.
   등록 거부 0건.
   - **이 등록은 색인을 만들기 전에 끝나 있어야 한다.** 색인을 만든 뒤에 단어를 추가하면
     이미 만든 색인에는 반영이 안 돼서 61만 건을 전부 다시 만들어야 한다.
     그래서 사전을 확정한 다음에 1-B로 넘어간다.
2. **금액 숫자를 살린다.** 쪼개기 도구는 `3,908,761` 을 조각낸다.
   공시 질문은 금액 자체가 검색어인 경우가 많아서, 원문에서 숫자를 따로 긁어
   **콤마 있는 형태와 없는 형태를 둘 다** 넣었다.
   - 다만 도구가 이미 같은 글자를 내놨으면 다시 넣지 않는다.
     그냥 붙이면 같은 숫자가 두 번 센 걸로 돼서 점수가 부풀려진다.
3. **불규칙 활용을 놓치지 않는다.** 쪼개기 도구는 불규칙 동사에 `VV-I`, `VV-R` 처럼
   꼬리표를 붙인다. `VV` 만 찾으면 이것들이 빠지므로 `-` 앞부분만 떼어 비교했다.
4. **한 건씩 부르지 않는다.** 1,000개를 통째로 넘겨야 여러 CPU가 나눠 일한다.
   for 반복문 안에서 하나씩 부르면 코어를 8개 줘도 1개만 쓴다.

네이버     14,950      삼성전자  13,927      삼성화재     13,871

`전자` 같은 일반명사가 수십만 회로 튀는 상황은 **없었다.**

### 그런데 다른 문제를 찾았다

빈도만으로는 안 보여서, 각 별칭이 **다른 낱말 속에 박혀서 걸리는 비율**을 따로 쟀다.
(한국어는 조사가 뒤에 붙으므로 "앞 글자가 한글이면 다른 낱말의 일부"로 보는 방식)

그리고 실제로 쪼개기 도구를 **사전 켠 상태 / 끈 상태**로 돌려 비교했다.
이게 결정적이었다.

**괜찮았던 것 — 걱정이 기우였던 부분**

`NC` 는 46,161회 중 90%가 `INC.`, `USANCE`, `FINANCIAL`, `AGENCY` 같은 **영어 단어 속**이었다.
그래서 위험해 보였는데, 실제로 돌려보니 쪼개기 도구는 영어 단어를 통째로 유지한다.
```
'XL8 INC. 및 공동기업'      사전 ON  -> ['xl','8','inc.','공동','기업']
                            사전 OFF -> ['xl','8','inc.','공동','기업']   (같음)
'LPL FINANCIAL WORLD'      ON/OFF 모두 -> ['lpl','financial','world']
'KB-KTB혁신기술...'        ON/OFF 모두 -> ['kb','ktb','혁신',...]
```
영문 별칭(`NC`, `KT`, `OCI`, `HMM`)은 등록해도 영어 단어를 부수지 않는다. **문제 없음.**

**진짜 문제 두 가지**

1. **`에스엠` 이 무관한 회사 이름을 부순다.**
```
'와이에스엠씨제일차 전자단기사채'
   사전 ON  -> ['와이','에스엠','씨','일','차','전자','단기','사채']   ← 부서짐
   사전 OFF -> ['와이에스엠씨제일차','전자','단기','사채']              ← 정상
```
`와이에스엠씨제일차`(YSMC)는 에스엠엔터테인먼트와 아무 상관이 없는 유동화회사다.
`엘에스엠트론`, `엘에스엠앤엠` 도 같은 식으로 부서진다. 이런 경우가 1만 2,517회 중 1,480회.

2. **`(주)` 가 붙은 표기를 등록하니 덩어리가 너무 커졌다.**
```
'에이치디현대중공업(주) 대표이사'
   사전 ON  -> ['에이치디현대중공업(주)','대표','이사']   ← 통짜 한 덩어리
   사전 OFF -> ['에이치디','현대중공업','주','대표','이사']
```
ON 쪽은 `현대중공업` 으로 검색해도 이 덩어리와 안 맞는다. **검색이 오히려 안 된다.**
이런 `(주)`·`㈜`·`주식회사` 포함 표기가 429개 중 **258개**다.

**그리고 짧은 한글 이름은 애초에 등록할 필요가 없었다.**
사전을 끄고 8개를 시험해보니 전부 이미 한 덩어리로 나온다.
```
기아 / 네이버 / 에스엠 / 이마트 / 카카오 / 케이티 / 하이브 / 현대차  → 8개 모두 정상
```
반대로 사전이 **꼭 필요한** 것은 도구가 쪼개버리는 이름들이다.
```
LIG넥스원 -> ['lig','넥스원']      한전기술 -> ['한전','기술']
시프트업  -> ['시프트','업']        파마리서치 -> ['파마','리서치']
세아베스틸지주 -> ['세아베스틸','지주']
```

### 제안 (사람 판단 대기 중이라 아직 안 고침)

- `config/aliases.yaml` 의 429개는 **그대로 둔다.** 회사 이름 찾기(`resolve_company`)는
  완전 일치로 비교하므로 별칭이 많을수록 좋고, 위 문제와 무관하다.
- **낱말 쪼개기 사전에 넣는 것만 걸러낸다.** 258개(법인격 표기 포함) + 8개(한글 3자 이하)를 빼면
  **163개**가 남는다. 이렇게 해도 **70개 회사 전부 최소 한 개 표기는 사전에 남는다.**

즉 파일 하나(429개)를 두 군데가 서로 다른 방식으로 쓰게 하는 것이다.

### (2) BM25 색인기를 만들었다

**BM25가 뭔가** — 임베딩(뜻이 비슷한 걸 찾는 방식)과 달리, **단어가 실제로 몇 번 나왔는지**로
점수를 매기는 방식이다. 흔한 단어는 점수를 깎고, 긴 문서는 불리하게 보정한다.
숫자·고유명사처럼 "그 글자 그대로" 찾아야 하는 질문에 강하다.

**외부 라이브러리를 쓰지 않고 직접 만든 이유:**
우리 검색기는 회사·연도로 **먼저 좁힌 뒤** 그 안에서만 점수를 낸다.
시중 라이브러리는 "전체에서 상위 몇 개"를 뽑는 걸 전제하므로,
회사 하나로 좁히면 결과가 0건이 된다.

**미리 계산해두는 구조.** 문서 쪽 가중치를 색인 만들 때 다 곱해둔다.
검색할 때는 질의어에 해당하는 **열만 꺼내서 더하면** 끝이라 빠르다.

**메모리 낭비를 피한 부분:**
- 값을 파이썬 리스트로 쌓으면 9천만 개에서 수 GB를 버린다 → `array.array` 사용
- 열을 꺼낼 때 `getcol()` 을 쓰면 호출마다 행렬 객체를 새로 만든다 → 내부 배열을 직접 잘라 씀

**색인 대상 글자:** 회사명 + 문서제목 + 문서 안 위치 + 본문.
본문은 임베딩용 텍스트가 아니라 `content` 를 쓴다.

만든 파일:

| 파일 | 하는 일 |
|---|---|
| `src/search/bm25_build.py` | 색인 만들기. `--limit` 로 일부만 시험 가능 |
| `src/search/bm25.py` | 검색. `score()` 는 **원점수 그대로** 돌려준다 |

`score()` 를 정규화하지 않은 이유 — 나중에 "답이 없는 질문"을 걸러낼 때
점수의 절대값이 필요하기 때문이다. 0점은 "질의어가 하나도 안 나옴"을 뜻한다.

### (3) 색인 만들기 전 행 순서 재검증

색인의 몇 번째 줄이 어느 조각인지는 순서로만 안다. 그래서 매번 다시 확인한다.

### 실패한 5b — 규칙 자체의 문제였다

"CJ제일제당 감사의견" 을 물으면 정정 전 원본에만 있는 감사보고서가 나와야 하는데 안 나왔다.
원인을 파보니 **검색은 완벽했다.** 순위를 매긴 직후 상태를 보면:

```
 1위  독립된 감사인의 감사보고서            ← 원본에만 있음 (정답)
 2위  내부회계관리제도 감사 또는 검토의견     ← 원본에만 있음 (정답)
 3~4위 목 차                            ← 원본에만 있음
 5위  분기보고서 > V. 회계감사인의 감사의견 등
 ...
 8위  [기재정정]사업보고서 > V. 회계감사인의 감사의견 등   ← 최신본
```

정답이 1·2위에 정확히 올라왔다. 그런데 규칙이 이렇게 돼 있다:

> 같은 보고서 묶음의 최신본이 후보에 이미 있으면, 그 묶음의 정정 전 자료는 버린다

8위에 최신본이 하나 있다는 이유로 **1·2위가 버려졌다.**
그런데 8위는 "V. 회계감사인의 감사의견 등"(본문 요약)이고 1위는 "독립된 감사인의 감사보고서"(첨부 원문)다.
**서로 다른 자리라 값이 충돌할 수가 없다.** 보완 관계지 대체 관계가 아니다.

반대쪽도 확인했다. "매출액" 질의에서는 이렇게 나온다:
```
 1~2위  [기재정정]사업보고서 > 영업부문 정보     ← 최신본
 9~10위 원본 > (첨부)연결재무제표 > 총매출액      ← 정정 전
```
여기서는 최신본이 위에 있고 정정 전 자료가 아래에 있다. 값 충돌이 실제로 가능한 경우다.

**즉 두 경우를 가르는 건 "묶음이 같은가"가 아니라 "누가 더 위에 있는가"였다.**

### 제안 (아직 안 고침 — 승인 대기)

규칙을 한 줄만 바꾸면 두 경우가 다 맞는다.

> 정정 전 자료를 버리는 조건: 같은 묶음의 최신본이 **그보다 위 순위에** 있을 때만

- "매출액" → 최신본이 1~2위, 정정 전이 9~10위 → **버림** (의도대로)
- "감사의견" → 정정 전이 1~2위, 최신본이 8위 → **안 버림** (의도대로)

임의로 정한 숫자가 안 들어가고, 원래 결정문의 두 예시가 그대로 재현된다.

다른 선택지도 있다:
- 아예 안 버리고 "정정 전 첨부본" 표시만 붙인다 (표시 기능은 이미 구현돼 있음)
- 현행 유지 — 다만 이 경우 감사보고서·첨부 재무제표 2만 6천 행이 사실상 검색되지 않는다

## 검색 결과를 눈으로 보는 도구 (2026-08-31)

`eval/probe_benchmark.py` 는 **몇 건 맞혔나**만 세고 본문을 보여주지 않는다.
"이 질문에 실제로 어떤 청크가 나오는가" 를 보려고 `eval/show_chunks.py` 를 새로 만들었다.
하이브리드 검색기를 그대로 태우고, 결과마다 보고서명·섹션 경로·본문·bm25/dense 점수를 찍는다.
골든셋 문항을 부르면(`--case`) 정답 문서·정답 숫자와 자동으로 대조해 `문서O/X` 표시가 붙는다.

두 도구의 실행법·인자·출력 읽는 법은 `docs/retrieval_probe_howto.md` 에 정리해뒀다.

측정한 것 (골든셋 표본 36문항, top-5, 문서 단위 적중):

| 필터 | doc@1 | doc@5 |
|---|---|---|
| 없음 | 0.14 | 0.36 |
| 회사만 | 0.19 | 0.58 |
| 회사 + 사업연도 | 0.61 | 0.89 |

틀리는 이유는 대부분 **회사·섹션은 맞는데 보고서 판이 틀린 것**이다.
같은 섹션이 분기·반기·사업보고서에 반복되니 본문만으로는 구분이 안 된다.
`fiscal_year` 를 주면 0.58 → 0.89 로 뛴다. 남은 실패도 같은 사업연도 안에서
분기·반기가 사업보고서를 밀어낸 경우다 — 보고서 종류 우선순위 신호가 더 필요하다.

`eval/probe_benchmark.py` 를 유형별로 돌린 결과(BM25만, top-20):

| 시나리오 | 정답 숫자가 코퍼스에 존재 | top-20 적중 |
|---|---|---|
| `search_closed` | 39/42 | 34/42 |
| `complex_closed` | 34/42 | 32/42 |
| `multi_closed` | 42/42 | 31/42 |
| `search_open` | 38/42 | 10/42 |

`search_open`(서술형)이 낮은 건 질의에 고유 용어가 없어 BM25 혼자로는 못 잡기 때문이다 — dense 몫이다.
`n/a` 로 찍히는 3건(LG에너지솔루션·두산로보틱스·레인보우로보틱스)은 검색 실패가 아니라
**채점 지표의 구멍**이다. 정답 숫자를 뽑는 정규식이 천 단위 콤마가 있는 숫자만 잡아서
`0.98 USD`, `13명(19%)`, `16개국·40개 대리점` 같은 작은 값이 통째로 빠진다. 청킹 문제가 아니다.
따라서 `정답 숫자가 코퍼스에 존재` 열은 상한이 아니라 **콤마 있는 숫자로 채점 가능한 문항 수**다.

## 단계 2 — 검색기와 HyperCLOVA X 를 잇는 최소 파이프라인 (2026-08-31)

### 왜 했나

여기까지는 "질문에 맞는 조각을 찾아오는가"만 봤다. 이제 확인할 것은 하나다.
**표가 들어 있는 조각을 그대로 넘겨주면 LLM 이 숫자를 제대로 읽어 오는가.**

Agent 를 완성하려는 게 아니다. 그래서 도구 호출(function calling)은 일부러 붙이지 않았다.
도구 목록이 아직 안 정해졌고, 그건 다음 단계 일이다. 검색 조건은 사람이 명령줄로 직접 준다.

### 인증 방식을 문서에서 먼저 확인했다

네이버 CLOVA Studio 는 버전에 따라 인증 방법이 두 가지다.

| 방식 | 헤더 |
|---|---|
| (a) 신방식 | `Authorization: Bearer nv-...` 하나 |
| (b) 구방식 | `X-NCP-CLOVASTUDIO-API-KEY` + `X-NCP-APIGW-API-KEY` 두 개 |

공식 문서(Chat Completions v3)를 확인한 결과 **(a) 신방식**이다.
`.env` 에 들어 있는 키가 `nv-` 로 시작하는 것도 여기에 맞는다.
나중에 바뀔 수 있으니 헤더를 만드는 자리를 함수 하나(`build_headers`)로 몰아뒀다.
바꿔야 하면 거기만 고치면 된다.

문서에서 확인한 값:

| 항목 | 값 |
|---|---|
| 주소 | `https://clovastudio.stream.ntruss.com/v3/chat-completions/{모델}` |
| 모델 | `HCX-005` (128k) · `HCX-DASH-002` (32k) · `HCX-007` (추론형, 128k) |
| 답이 들어 있는 자리 | `result.message.content` |
| 성공 표시 | `status.code == "20000"` |

### 만든 것

| 파일 | 하는 일 |
|---|---|
| `src/agent/clova.py` | HyperCLOVA X 호출. 실패해도 예외를 던지지 않고 `{"ok": False, ...}` 로 돌려준다 |
| `src/agent/context.py` | 검색 결과를 `<document>` 묶음 글자열로 조립 |
| `prompts/system_min.txt` | 시스템 프롬프트 |
| `eval/quick_qa.py` | 검색 → 조립 → 호출을 한 번에 훑어보는 명령줄 도구 |
| `eval/test_context.py` | 조립기 단위 검증 11개 |

### 열쇠(API 키)를 다루는 규칙

- 환경변수 `CLOVA_API_KEY` 로만 읽는다. 코드·주석·로그 어디에도 값이 없다
- 헤더를 통째로 찍지 않는다. 찍어야 하면 `nv-********(len=39)` 처럼 가린다
- 키가 없거나 빈 칸이면 **부르기 전에** 멈춘다.
  빈 키로 부르면 401 이 돌아오는데, 그걸 "API 가 죽었나" 로 오해하기 쉽다
- 윈도우에서 만든 `.env` 는 끝에 공백이나 따옴표가 붙는 일이 있어서 떼고 쓴다

### 조각을 어떤 모양으로 넘기는가

```
※ 자동 주석(공시 원문 아님): 제17기=2023년, 제16기=2022년 · 단위 천원 · 연결기준
<document id="2" source="[CJ제일제당 분기보고서 (2023.03), 2023-05-15, 접수번호 20230515002270]"
          section="III. 재무에 관한 사항 > 2. 연결재무제표">
| 구분 | 제 17 기 1분기 | 제 16 기 1분기 |
...
</document>
```

자동 주석을 **태그 바깥 윗줄**에 둔 이유가 중요하다.
이건 공시 원문에서 뽑은 게 아니라 메타데이터로 계산한 추정이다.
태그 안에 넣으면 모델이 원문과 구분할 수 없다.

본문에 `</document>` 라는 글자가 들어 있으면 `[/document]` 로 바꾼다.
안 바꾸면 그 뒤 문장이 "공시 내용"이 아니라 "나에게 주는 지시"로 읽힐 수 있다.

### 당기 연도를 무엇으로 잡았나 — 사양과 다르게 했다

사양에는 "base_year 를 당기 연도로 삼는다" 고 되어 있었다.
그런데 이 리포에서 `base_year` 는 **접수 연도**다 (CLAUDE.md 와 `hybrid.py` 에도 같은 경고가 있다).
2024 사업연도 사업보고서는 2025년에 접수되므로 `base_year=2025` 다.
이걸 당기로 쓰면 "제56기=2025년" 같은 틀린 주석이 나간다.

그래서 보고서 이름의 `(2024.12)` 에서 뽑은 `fiscal_year` 를 당기 연도로 썼다.
`fiscal_year` 가 없는 문서(주요사항보고서 등)는 접수 연도로 때우지 않고 **주석을 통째로 뺐다.**
틀린 연도를 지어내는 것보다 없는 게 낫다.

### 검증 (실제 호출 전에 전부 끝냈다)

| 확인할 것 | 결과 |
|---|---|
| 조립기 단위 검증 11개 | 전부 통과 |
| CJ제일제당 분기보고서(2023.03) 재무제표 조각 | `제17기=2023년, 제16기=2022년 · 단위 천원 · 연결기준` 나옴 |
| 주석이 `<document>` 바깥 윗줄에 있는가 | 그렇다 |
| 기수 표기가 없는 조각 | 주석 생략, 예외 없음 |
| 실제 조각 5,488개로 대량 확인 | 예외 **0건** (주석 생성 358 / 생략 5,130) |
| KB금융 조각 1,682개 | 주석 61 / 생략 1,621 · 예외 0건 |
| 본문에 `</document>` 를 넣은 가짜 결과 | `[/document]` 로 치환됨 |
| 키를 비우고 실행 | 인덱스도 안 올리고 즉시 중단, 호출 시도 안 함 |

### 실제 호출 1건 — 숫자를 제대로 읽었다

질문: "2023년 1분기(제17기 1분기) 연결 기준 매출액과 영업이익은 각각 얼마인가?"
(CJ제일제당 분기보고서 2023.03, 접수번호로 문서를 특정)

답:

| 항목 | 모델이 답한 값 | 원문 제17기 1분기 | 맞나 |
|---|---|---|---|
| 매출액 | 7,071,159,309천원 | 7,071,159,309 | 맞다 |
| 영업이익 | 252,780,577천원 | 252,780,577 | 맞다 |
| 전분기 매출액 | 6,979,894,271천원 | 6,979,894,271 | 맞다 |
| 전분기 영업이익 | 435,659,992천원 | 435,659,992 | 맞다 |

**당기 열과 전기 열을 안 헷갈렸다.** 이게 이번 단계에서 보고 싶었던 것이다.
같은 조각 안에 "제16기 6,979,894,271" 이 두 번 나오고(부문별 표에도 나온다) 그걸 당기로
착각하기 딱 좋은 배치인데 제대로 골랐다.

프롬프트 2,200토큰 · 답변 138토큰 · 검색 4.0초 · 호출 3.7초.

### 그런데 두 가지가 걸린다

**(1) 근거 표기를 시킨 대로 안 붙인다.**
시스템 프롬프트는 `[회사명 보고서명, 접수일, 접수번호 ...]` 를 요구했는데
모델은 `[자료: CJ제일제당 분기보고서 (2023.03)]` 만 붙였다. 접수일·접수번호가 빠졌다.
채점이 근거 표기를 본다면 여기서 점수가 샌다.

**(2) 자동 주석의 연도 환산이 5개 중 1개꼴로 틀린다. — 이게 더 큰 문제다.**

"조각에 나온 가장 큰 기수 = 당기" 라는 규칙이 문제다.
조각이 문서의 당기를 안 담고 있으면 그대로 어긋난다.

실제로 정기보고서 40개를 통째로 훑어 재봤다.
문서의 진짜 당기 기수(재무제표 절에서 뽑음)와 조각의 최대 기수를 비교한 결과:

| | 주석 붙은 조각 | 기준이 어긋난 것 |
|---|---|---|
| 전체 | 1,085 | 232 (**21.4%**) |
| III. 재무에 관한 사항 | 625 | 27 (4.3%) |
| VI. 이사회 등 | 99 | 89 (89.9%) |
| V. 회계감사인의 감사의견 | 86 | 19 |

예: CJ제일제당 분기보고서(2023.09)는 당기가 제17기인데,
제16기만 실린 조각에 "제16기=2023년" 이라고 붙는다. 실제로는 2022년이다. **1년씩 밀린다.**

시스템 프롬프트에 "주석과 원문이 다르면 원문을 따르라" 고 적어두긴 했지만,
틀린 힌트를 넣어두고 모델이 무시해 주길 바라는 건 좋은 설계가 아니다.

고치는 방법은 어렵지 않다. 기준을 **조각이 아니라 문서 단위**로 잡으면 된다.
문서마다 재무제표 절에서 당기 기수를 한 번 구해 표로 만들어두고,
조각의 기수를 그 표에 대고 환산한다. 위 측정 스크립트가 이미 그 계산을 하고 있다.

다만 사양을 바꾸는 일이라 **승인을 받고 고친다.** 지금 코드는 사양대로 둔 상태다.

## 단계 2-B — 실사용에서 나온 결함 고치기 (2026-08-31)

### 왜 했나

단계 2에서 파이프라인은 돌았지만 실제로 질문을 던져 보니 네 가지가 틀렸다.

| 증상 | 실제로 나온 오답 |
|---|---|
| 다른 표의 단위를 가져다 씀 | KB금융 자기자본을 `2,090,558십억원` (백만원 표 값 × 십억원 표 단위 = 1000배) |
| 행 이름을 안 보고 값을 가져옴 | 매출액을 물었는데 `비유동자산 61,105,339` 를 답함 |

여기에 더해 자동 주석의 연도 환산이 5개 중 1개꼴로 틀리는 문제(단계 2에서 발견)와,
정정 전 자료라는 경고가 검색 메타에만 있고 LLM 프롬프트에는 안 들어가던 문제를 함께 고쳤다.

### 1. 기수 -> 연도 환산을 '문서 단위'로 바꿨다

**무엇이 문제였나.** 옛 규칙은 "조각에 나온 가장 큰 기수 = 당기" 였다.
조각이 문서의 당기를 안 담고 있으면 그대로 어긋난다.
CJ제일제당 분기보고서(2023.09)는 당기가 제17기인데, 제16기만 실린 조각에
"제16기=2023년" 이 붙었다. 실제로는 2022년이다. **1년씩 밀린다.**

**어떻게 고쳤나.** 문서마다 재무제표 절에서 당기 기수를 한 번 구해 표로 만들어 두고,
조각의 기수를 그 표에 대고 환산한다.

- 만드는 법: `python -m src.agent.context --build`
- 표 파일: `data/index/doc_fiscal_map.json` — `{doc_id: {current_ki, fiscal_year, rcept_no}}`
- 전량(청크 614,578개)을 훑는 데 **14초**. 정기보고서 접수번호 1,054건 중 1,049건 확보

한 보고서가 doc_id 여러 개로 쪼개지는 경우가 있다(본문 + 첨부 감사보고서 등, 210건).
같은 접수번호면 같은 보고서이므로 접수번호 단위로 당기 기수를 모아
그 접수번호에 딸린 doc_id 전부에 같은 값을 준다.

**모르면 지어내지 않는다.**

| 상황 | 동작 |
|---|---|
| 문서가 표에 없다 | 주석 생략 (접수 연도로 때우지 않는다) |
| 조각의 기수 > 문서의 당기 기수 | 주석 생략 + `reports/annotate_era_overflow.jsonl` 에 기록 |
| 검색 결과의 사업연도 ≠ 표의 사업연도 | 주석 생략 + 기록 (표가 낡았다는 신호다) |
| 이벤트 공시(주요사항·지분·거래소) | 애초에 표에 안 넣는다 |

### 2. 측정 스크립트의 절 판정에 구멍이 있었다

당기 기수를 "재무제표 절"에서 뽑는데, 원래 측정 스크립트는 section_path 를
통째로 이어붙여 '재무제표' 라는 글자가 있는지 봤다. 그러면 **각주 문구가 섞인다.**

LG생활건강 `II. 사업의 내용 > 3. 원재료 및 생산설비` 의 각주가
"…'3. 연결재무제표 주석' 중 '16. 유형자산'을 참조" 라서 재무제표 절로 오인됐고,
그 표의 `예상 투자액(제24기)`(내년 계획)이 당기 기수를 1 올려버렸다.
LG생활건강 3개 연도가 전부 1년씩 밀려 있었다.

절 판정을 **section_path 의 1~2번 칸(장·절 제목)만** 보도록 좁혔다.

### 8. 공식 문서 + 실제 호출로 확인한 것

호출 가능 여부는 문서를 믿지 않고 **이 계정 키로 직접 찔러 봤다.**

| 모델 | 이 계정에서 | 입력 상한 | 출력 상한 | 도구 호출 |
|---|---|---|---|---|
| HCX-005 | 됨 | 128,000 | 4,096 | 됨 |
| HCX-DASH-002 | 됨 | 32,000 | 4,096 | 됨 |
| HCX-007 | 됨 (조건부) | 128,000 | 32,768 | 됨 (`thinking.effort="none"` 필요) |
| HCX-003 / DASH-001 | 안 됨 | 7,600 / 3,500 | — | 없음 |

- HCX-003·DASH-001 은 `40084 Unsupported API for model` — v3 API 를 안 받는다
- HCX-007 은 `maxTokens` 를 거부하고 `maxCompletionTokens` 를 요구한다
  (`40001 Invalid parameter: maxTokens`). `clova.py` 가 모델을 보고 알아서 바꾼다
- HCX-007 은 `tools` 와 추론을 같이 못 쓴다 (`40001 Invalid parameter: tools, thinking`).
  `thinking: {"effort": "none"}` 을 같이 보내면 도구 호출이 된다
- 도구 호출은 `maxTokens` 를 1024 이상으로 줘야 한다 (문서 명시)

**컨텍스트 여유.** 지금 프롬프트는 5,200토큰 수준이다.
HCX-005 의 128,000 토큰 대비 4% 라서 Agent 가 도구 결과를 쌓아도 여유가 크다.
DASH-002(32,000)는 도구 결과가 몇 번 쌓이면 위험하다.

**도구 호출 왕복 스키마 — 실제 2턴을 돌려 확인했다.**

```
요청:  "tools": [{"type":"function","function":{"name","description","parameters"}}]
       "toolChoice": "auto" | "none" | {"type":"function","function":{"name":...}}
응답:  result.message.toolCalls[].{id, type, function:{name, arguments}}
       result.finishReason == "tool_calls"
되돌려주기:
  {"role":"assistant","content":"","toolCalls":[그 toolCall 그대로]}
  {"role":"tool","toolCallId":"call_...","name":"함수명","content":"결과 문자열"}
```

**주의 — OpenAI 와 다르다.** `function.arguments` 가 **JSON 문자열이 아니라 객체**로 온다.
`json.loads()` 를 걸면 터진다. 9/3 Agent 루프에서 여기 걸리기 쉽다.

`chat()` 에 `extra=` 를 열어 뒀다. `tools`·`toolChoice`·`thinking` 을 그대로 실어 보내고,
도구 호출이 오면 반환 dict 의 `tool_calls` 로 받는다.

**요금은 확인하지 못했다.** 공식 문서(`clovastudio-model`, `clovastudio-spec`)와
상품 페이지 어디에도 토큰당 단가표가 없다. 문서는 "포털 > 서비스 > AI Services >
CLOVA Studio 요금 안내" 를 보라고만 한다. 그 페이지는 로그인·JS 렌더라 못 읽었다.
**추측해서 적지 않는다. 콘솔에서 사람이 확인해야 한다.**

### 왜 했나

여기까지 검색기를 고칠 때마다 "좋아진 것 같다" 는 말만 했다. 근거가 없었다.
`probe_benchmark.py` 는 정답 숫자가 본문에 있는지로 대충 쟀고,
`src/eval/run_eval.py` 는 "섹션 제목에 기대 키워드가 걸렸나" 라는 약한 기준을 썼다.
둘 다 **어느 청크가 정답인지** 를 모른다.

그래서 사람이 직접 정답 청크를 찍어 주는 골든셋을 만들기로 했다.
질문은 이미 있는 것(`bench_q_part*.json` 318문항)을 쓰고, 정답만 사람이 고른다.
**도구는 정답을 짓지 않는다.** 화면에 검색 결과를 띄우고 번호를 받아 적을 뿐이다.

### 만든 것

| 파일 | 하는 일 |
|---|---|
| `eval/label_helper.py` | 30문항 표본추출 + 라벨링 화면 |
| `eval/run_eval.py` | 골든셋으로 채점 (recall/MRR/지연, 구간별, 실패 목록, 가중치 비교) |
| `eval/golden_todo.jsonl` | 뽑힌 30문항 (시드 고정이라 언제든 재현) |

### 표본을 뽑는 게 생각보다 까다로웠다

목표 배분은 공시그룹 12/8/5/5, 유형 12/10/8, **회사 30개 전부 다르게**,
금융·보험·엔터 5문항 이상이었다.

그런데 **후보 풀에 회사가 15개밖에 없다.** `bench_q_part01~03` 이 알파벳순으로
CJ제일제당~OCI홀딩스까지만 덮고 있고, 나머지 55개사 문항은 아직 없다.
30문항을 서로 다른 회사로 채우는 건 산술적으로 불가능하다.

게다가 그 15개사 중 금융·보험은 KB금융 하나, 엔터는 JYP Ent 하나뿐이다.
회사당 2문항으로 제한하면 이 업종에서 최대 4문항밖에 안 나와서 "5문항 이상" 과 충돌한다.

**처음엔 탐욕적으로 담았더니 두 가지가 어긋났다.**
회사가 최대 3문항까지 쏠렸고, 더 나쁘게는 **같은 문항이 두 번 뽑혔다**(HMM 문항 하나).
그래서 최대유량 문제로 다시 짰다.

```
source → (공시그룹,유형) 칸 [용량=뽑을 개수] → 회사 [용량 1] → sink [용량=회사별 상한]
                                                      ↑
                                    여기가 1이라 같은 칸에서 같은 회사가 두 번 안 나온다
```

회사별 상한을 한 번에 3으로 올리지 않고 **사다리로 올린다** — 먼저 전부 2로 시도하고,
안 되면 금융·엔터 회사만 3으로 풀고, 그래도 안 되면 전부 3으로. 그 결과:

| | 목표 | 실제 |
|---|---|---|
| periodic / exchange / major / holding | 12 / 8 / 5 / 5 | **12 / 8 / 5 / 5** |
| search_closed / search_open / multi_closed | 12 / 10 / 8 | **12 / 10 / 8** |
| 금융·보험 + 엔터 | 5 이상 | **5** |
| 서로 다른 회사 | 30 | **15** (풀 전체. 불가능) |
| 한 회사 최대 | 1 | **3** (JYP Ent 하나뿐, 나머지는 2 이하) |

3문항인 회사가 JYP Ent 하나인 건 우연이 아니다. 엔터 회사가 그것뿐이라
5문항을 맞추려면 KB금융 2 + JYP 3 밖에 방법이 없다.

시드 `20260904` 고정. `--seed` 로 바꿀 수 있고 화면에 항상 찍는다.

### 한 문서 상한을 풀어야 했다 — 안 그랬으면 못 쓸 뻔했다

검색기는 한 문서에서 2청크까지만 올린다(`hybrid.PER_DOC=2`).
결과를 한 문서가 독점하지 못하게 하려는 옳은 설계다.

그런데 라벨링은 **접수일로 문서를 하나로 좁혀 놓고** 그 안에서 정답 청크를 고르는 일이다.
상한 2가 그대로 걸리면 250청크짜리 사업보고서에서 후보가 2~6개만 뜬다.
top-20 을 보여준다고 해놓고 실제로는 6개를 보여주는 셈이고,
그 상태로 recall 을 재면 **정답이 원래 상한에 막혀 안 보인 것을 "검색 실패" 로 기록**하게 된다.

라벨링과 평가에서는 상한을 푼다(`per_doc`). 설정이 다르면 숫자를 비교하면 안 되므로
평가 리포트 맨 위에 이 값을 항상 찍는다.

### 보조 grep — 이게 없으면 recall 이 부풀려진다

`g <문자열>` 은 검색기를 거치지 않고 그 문서의 청크를 직접 훑는다.
숫자는 콤마 있는 형태와 없는 형태를 모두 시도한다(`3,908,761` / `3908761`).

없으면 어떻게 되나. **검색기가 top-20 에 올려준 것 중에서만 정답을 고르게 된다.**
정답이 코퍼스에 있는데 검색기가 못 찾은 경우를 사람이 확인할 방법이 없고,
그러면 그 문항은 조용히 사라져서 recall 이 실제보다 높게 나온다.
`n`(top-20 안에 없음)으로 기록하는 것 자체가 중요한 데이터인데, 그걸 못 남긴다.

### 평가 지표를 둘로 나눴다

한 문항의 정답 청크가 여러 개일 수 있어서 하나로 뭉뚱그리지 않는다.

- `hit@k` — top-k 안에 정답이 **하나라도** 있는 문항 비율. "찾긴 찾았나"
- `recall@k` — 문항별 (top-k 안의 정답 수 / 그 문항의 정답 수) 평균. "여럿 중 몇 개나"

정답이 하나인 문항에서는 둘이 같다.

`gold_chunk_ids` 가 빈 문항(라벨링에서 `n`)은 채점에서 빼되 **개수를 반드시 따로 보고한다.**
조용히 빼면 recall 이 부풀려진다. 회사명 해석 실패도 중단하지 않고 실패로 기록하고 넘어간다.

| 확인할 것 | 결과 |

| 배분 목표 | 공시그룹·유형 전부 정확히 일치, 금융·엔터 5문항 |

## 단계 3-D — 인접 청크 보강 (2026-09-01)

### 왜 했나

앞선 조사에서 청커가 표 제목과 표 본문을 갈라놓는 걸 확인했다.

| | 개수 | 비율 |
|---|---|---|
| 제목 없이 곧바로 표 행으로 시작하는 청크 | 361,954 | 58.9% |
| 제목만 있고 표는 다음 청크에 있는 청크 | 17,081 | 2.8% |

앞의 것이 위험하다. 표 안에 `(단위 : 백만원)` 이 없으면 LLM 이 단위를 추측한다.
실제로 KB금융 자기자본을 **백만원 표에서 읽고 십억원을 붙여 1000배 틀린** 적이 있다.

청킹을 다시 하는 게 정답이지만 전량 재임베딩(614,578청크)이 필요해 마감에 안 맞는다.
그래서 **검색 결과를 조립할 때만** 인접 청크에서 필요한 줄을 끌어오기로 했다.

### 규칙을 좁게 잡았다

"앞뒤를 무조건 붙인다" 는 절대 안 된다. 남의 표 단위가 섞이면 지금보다 나빠진다.

**규칙 1 — 표 청크에 헤더를 붙인다.**
검색된 청크가 `|` 로 시작하고 그 안에 `(단위` 가 없을 때만, 같은 `doc_id` 안에서
최대 2칸 거슬러 올라가 단위·제목 **줄만** 뽑아 표 앞에 붙인다. 청크 전문은 안 붙인다.

**규칙 2 — 제목 청크에 표를 붙인다.**
검색된 청크가 150자 미만이고 표가 없을 때만, 바로 다음 청크가 표를 담고 있으면 이어 붙인다.
다음 청크가 표가 아니면 아무것도 안 한다.

둘은 조건이 배타적(하나는 표로 시작, 하나는 표가 없음)이라 동시에 걸리지 않는다.
`doc_id` 경계는 절대 넘지 않는다.

붙인 부분은 원문이 아니므로 `[인접 청크에서 보강: 단위·제목]` / `[여기부터 검색된 청크 원문]`
표시를 남긴다. 출처 `chunk_id` 는 원래 검색된 것을 그대로 쓴다.

### 1차 규칙은 틀린 단위를 붙였다 — 무작위 30개 육안 확인에서 잡았다

처음엔 "앞 청크가 표로 시작하면 중단" 으로만 막았다. 30개를 눈으로 보니 구멍이 있었다.

**두산로보틱스** — 앞 청크가 `가. 회계감사인의 명칭 및 감사의견 | 표…` 였다.
첫 줄이 `|` 로 시작하지 않아 중단 조건에 안 걸렸고, 그 안에 들어 있던 **다른 표의**
`(단위: 천원, 시간)` 이 딸려 왔다. 현재 청크는 감사인 커뮤니케이션 표(일자/참석자/방식)로
금액 단위가 아예 없다. **막아야 할 실패 그 자체다.**

**하이브** — 표 데이터 행 `| 부여일의 기초자산 공정가치 (단위: 원) | … | 193,000 | …` 이
`(단위` 를 품고 있어 캡션으로 뽑혔다.

**이마트 / HD현대중공업** — 단위도 없는 긴 산문 한 줄, 날짜 한 줄이 '제목' 으로 붙었다.

세 가지를 조였다.

1. **표 행은 캡션이 아니다** — `|` 가 2개 이상인 줄은 안 뽑는다
2. 단위 없는 '제목' 줄은 **120자 이하**일 때만 인정한다
3. 앞 청크가 표를 품고 있으면 두 경우만 허용한다
   - (a) 그 표의 **마지막 행 뒤**에 붙은 꼬리 캡션 — 우리 표를 여는 제목이다
   - (b) 우리 청크가 그 표의 이어짐(첫 표 행이 글자 그대로 같다) — 표 앞 단위가 맞다
   둘 다 아니면 붙이지 않고 거슬러 올라가기를 멈춘다

### 그러고 나서 KB금융이 여전히 안 붙었다 — 한 칸이 모자랐다

검증 3에서 정작 목표였던 자본변동표에 단위가 안 붙었다. 청크가 이렇게 쪼개져 있었다.

```
row 55134  자본변동표 / 제 18 기 반기 … / (단위 : 백만원)     ← 95자, 표 없음
row 55135  | 구분 | 자본 자본금 | …                          ← 표 1부
row 55136  | 구분 | 자본 자본금 | …  (헤더 반복)             ← 표 2부, 검색된 청크
```

55136에서 한 칸 올라가면 55135 — 같은 표의 이어짐인 건 맞게 알아냈는데,
그 청크의 표 **앞에** 아무것도 없어서 빈손으로 멈춰버렸다.
같은 표라는 게 확인됐으면 **한 칸 더 올라가도 된다**. 그렇게 고치니 55134의
`(단위 : 백만원)` 을 찾아왔다.

## 단계 3-G — found_by_grep 7건 원인 분석 (2026-09-02)

### 왜 했나

골든셋 18건 첫 평가에서 지표가 두 덩어리로 갈렸다.

| | recall@20 |
|---|---|
| `found_by_grep` 7건 (검색으로 못 찾아 원문 grep 으로 찾은 것) | **0.286** |
| 그 외 11건 | **1.000** |

나머지 11건은 top-20 에 100% 들어온다. 즉 지금 검색기의 문제는 "전반적으로 약하다" 가
아니라 **특정 유형에서 완전히 못 찾는다** 는 쪽이다. 그 7건만 갈랐다. 검색기는 안 고쳤다.

### 가르는 방법

각 문항마다 다섯 가지를 봤다.

1. 골든셋의 `search_query` 로 검색했을 때 정답 청크 순위 (top-500 까지 파서)
2. 정답 청크와 1위 청크의 vec / bm25 **원점수**, 그리고 후보 안에서 각각의 순위
3. 정답 청크의 `section_path` 와 본문
4. `ground_truth` 의 정답 숫자로 검색했을 때 순위 — **숫자가 색인에 있는지** 확인
5. 정답 청크의 절 제목·표 내용에서 핵심어를 뽑아 손으로 쓴 "이상적 검색어" 로 재검색

5번에서 top-10 에 들어오면 (a) 검색어 문제, 안 들어오면 (b) 검색기 문제.

### 먼저 확인된 것 — 색인은 멀쩡하다

청킹이나 임베딩이 정답을 통째로 빠뜨린 경우는 **한 건도 없다.**

### (a) 4건 — 검색어가 문제였다

- **고려아연** 99위 → 4위. 검색어가 `II. 사업 2. 주요 제품 서비스 품목 매출액` 로
  절 제목만 담았다. `주요 제품 아연 연 은 금 매출액 비중` 처럼 **제품명**을 넣으면 잡힌다
- **CJ제일제당** 25위 → 3위. 표의 행 이름만 있고 표의 다른 항목이 없었다.
  `매출액 영업이익` 을 넣으니 표를 짚는다
- **레인보우로보틱스** 51위 → 6위. `초정밀`·`총판`·`16개국` 같은 본문 고유어가 빠져 있었다
- **NAVER** 는 원래 검색어로도 **3위**였다. 사람이 grep 을 썼을 뿐 검색기는 이미 찾았다

### (b) 3건 — 원인이 둘로 갈린다

**(b-1) 정답이 표가 아니라 '사업의 개요' 산문에 묻혀 있다 — 삼성화재·삼성생명**

둘 다 정답 청크가 `II. 사업의 내용 > 1. 사업의 개요` 다. 청크 앞부분이 회사 일반 소개고
정답 숫자는 중간에 있다.

| | 청크 길이 | 정답이 있는 위치 | vec 순위 |
|---|---|---|---|
| 삼성화재 | 1,462자 | 32~44% 지점 | 424 |
| 삼성생명 | 1,143자 | 21~25% 지점 | **1168** |

**임베딩이 청크 앞머리의 일반론에 쏠린다.** 게다가 보험사라 `장기보험`·`사망보험` 같은 말이
그 회사 청크의 4~7%(수백 개)에 흩어져 있어 BM25 변별력도 없다.
결정적으로, **같은 단어를 더 많이 가진 절이 따로 있다** — 삼성생명의 이상적 검색어 top-10 은
`2. 영업의 현황`(수입보험료 표가 보통 실리는 절)으로 채워진다.
검색기는 **더 그럴듯한 절을 고른 것**이고, 이번 문항의 답이 개요 산문에 있었던 게 예외다.
삼성화재는 이상적 검색어를 넣으면 오히려 **>500위**로 더 밀린다 —
`보험금융수익`·`재보험서비스결과` 절이 그 단어를 훨씬 진하게 갖고 있기 때문이다.

**(b-2) 같은 절이 여러 보고서에 반복된다 — SK텔레콤**

정답 청크는 **맞는 표**다(영업부문별 무선/유선/기타). 그런데 이상적 검색어 top-10 중
**9개가 같은 `4. 부문정보 (연결)` 절의 다른 보고서판**이다 —
사업보고서 2023.12 / 2024.12 / 2025.12, 분기보고서 2023.03 / 2023.09 / 2025.03 / 2026.03 …
접수일·사업연도 필터가 없으면 제42기를 고를 신호가 없다.
JYP Ent 라벨링 때 `매출 및 수주상황` 이 12개 보고서에 반복돼 top-20 을 채웠던 것과 같은 문제다.

### 곁가지로 보이는 것 — dense 가 BM25 보다 나쁘다

7건 중 5건에서 정답 청크의 **vec 순위가 bm25 순위보다 나쁘다.**
삼성생명은 1168위 대 5위로 극단적이다.
가중치 sweep 에서 `(w_vec=1, w_bm25=2)` 가 가장 좋았던 것과 같은 방향이다.
다만 18건 기준이라 지금 가중치를 바꾸지는 않는다.

### safe_tool — 이게 핵심이다

평가 중 도구에서 예외가 나면 그 문항은 0점이다. LLM 은 스키마에 없는 인자를 지어내고,
문자열이어야 할 자리에 숫자를 넣고, 필수 인자를 빼먹는다. 전부 여기서 흡수한다.

- 함수가 `**kwargs` 를 안 받으면 시그니처에 없는 키는 **버리고** note 에 적는다
- `TypeError` → `{"status":"error","note":"인자 오류: …"}`
- 그 밖의 예외 → traceback 은 stderr 로 남기고(규칙 9) 반환은 error dict
- 반환이 dict 가 아니거나 키가 모자라면 채워서 모양을 맞춘다

실제로 잡탕 인자를 넣어보니 이렇게 흡수한다.

```
resolve_company(expression=None, corp_name=12345, fiscal_year='이천이십사',
                limit='많이', query=[...], 없는키={...}, top_k=-3, series_of=2026...)
→ {"status":"error", "note":"name 이 비어 있다 · 모르는 인자를 버렸다: [...]"}
```

### calculate — ast.literal_eval 은 못 쓴다

`literal_eval` 은 **리터럴만** 평가한다. `1+1` 같은 산술식은 그냥 죽는다.
그래서 `ast.parse(mode="eval")` 로 트리를 만들고 **노드 화이트리스트**로 걷는다.
Add/Sub/Mult/Div/FloorDiv/Mod/Pow/USub/UAdd 와 숫자 리터럴만 통과시킨다.
`__import__('os').system('ls')` 는 Call 노드라 그 자리에서 막힌다.

**거듭제곱은 계산하기 전에 막는다.** `2**999999999` 는 값을 만들기 시작하면 프로세스가
몇 분 멈추고 메모리를 다 먹는다. 평가 중 프로세스가 멈추면 그 문항만 0점이 아니라
**평가 전체가 죽는다.** 지수 8 초과, 밑 1e6 초과면 계산 전에 거절한다.
실측 0.000초에 거절된다.

콤마는 지운다 — 공시 숫자는 `3,477,640` 처럼 들어오는 게 정상이다.

### list_disclosures — 세는 일은 파이썬이 한다

"정정공시가 몇 건인가", "유형별 비중이 얼마인가" 는 검색으로 풀면 안 된다.
검색은 top-k 만 돌려주므로 **세는 일에 구조적으로 부적합**하다.
manifest 에 다 있으니 그냥 센다. `total` 과 `by_subtype` 은 언제나 전량 기준이고
`limit` 은 `results` 만 자른다. 비중 합은 반올림 잔돈을 가장 큰 항목이 흡수해 정확히 1.0.

`series_of=<접수번호>` 는 같은 계열([기재정정] 접두를 뗀 보고서명이 같은) 문서를
접수일순으로 전부 준다. 정정 이력 추적용이다.

**사업연도 주의.** manifest 의 `base_year` 는 접수 연도다. 사업연도로 거르려면
report_nm 의 `(2024.12)` 를 봐야 하고, 그 로직은 `context.fiscal_year_of` 를 재사용했다.

### tools.json — description 을 길게 쓴 이유

LLM 은 이 문장만 보고 도구와 인자를 고른다. 짧게 쓰면 회사명을 query 에 넣고
접수일을 빼먹는다. 실제로 단계 2에서 그랬다. search_disclosure 는 851자를 썼고
아래를 명시했다.

- 회사명·연도·날짜는 query 가 아니라 별도 파라미터로
- 회사·연도가 둘 이상이면 나누어 여러 번 호출
- 접수일·접수번호가 질문에 있으면 반드시 넣을 것 (안 넣으면 다른 시점 값을 답한다)
- 검색어는 공시 원문 표현으로 ('설비투자' → '유형자산의 취득')
- 절 제목만 넣지 말고 본문 고유어를 함께 ('주요 제품 및 서비스' → '주요 제품 아연 은 금 매출액')
- '요약해줘' 같은 요청 동사는 제외
- `include_superseded` 는 정정 전후 비교 질문에서만 true

마지막 두 개는 **3-G 원인 분석에서 나온 것**이다. (a) 검색어 문제 4건이 전부
"절 제목만 담고 본문 고유어를 안 담아서" 였고, (b-2) SK텔레콤은 시점을 안 좁혀서였다.

### 재호출 차단을 두 번 고쳤다 — 캐시 '결과' 를 주면 안 된다

**모델이 같은 문서를 또 보고는 "아직 못 찾았다" 로 읽어 같은 검색을 3번 반복했다.**
6회 한도 중 2회를 그렇게 낭비했고, 그 탓에 HTTP 429 레이트리밋까지 맞았다.

결과 없이 `status="error"` 로 끊도록 바꿨다.

```
{"status":"error","results":[],
 "note":"이미 같은 인자로 조회했다. 그 결과는 위 대화에 그대로 있다.

### 마지막 턴 형식 리마인더 (2026-09-02)

도구 결과가 12,000자쯤 쌓이면 4,000자짜리 시스템 프롬프트가 멀어져서
(1) 사칙연산을 calculate 없이 암산하고 (2) 근거 절을 빠뜨렸다.
가까이에서 한 번 더 말해 준다.

**넣는 자리 — 도구 결과를 다 넣은 직후, 딱 한 번.**
"모델이 답변만 내놓으려는 턴" 은 불러 보기 전엔 알 수 없다. 그걸 알아내려면
한 번 부르고 버린 뒤 다시 부르는 셈이라 LLM 호출이 두 배가 된다.
도구 결과가 들어온 직후면 다음 턴이 십중팔구 답변 턴이고, 아니어도 손해가 없다
(모델이 도구를 더 부르면 루프는 그냥 계속 돈다). 플래그 하나로 중복을 막았고
도구 호출 카운트에는 넣지 않는다.

   분명히 들어가 있는데(확인함) 지켜지지 않는다.

3. **r2 가 fiscal_year 를 2025 로 넣었다.** 질문은 "2024년" 인데 두 번 다 2025다.

### 형식을 LLM 에게 맡기지 않는다 (2026-09-02)

세 문제를 순서대로 고쳤다.

**[1] 근거 절을 파이썬이 만든다.**
모델에게 맡겼더니 출처가 둘 이상일 때 대괄호를 떼먹었다(실측 2/2).
`attach_sources()` 가 모델이 쓴 근거 목록을 떼어내고, 도구가 돌려준 `sources` 로
다시 붙인다. 문자열은 `context.fmt_source()` 가 만든 것을 글자 그대로 쓴다.
"실제로 인용한 것" 은 답변 본문에 접수번호(14자리)가 있는지로 가른다.
하나도 안 맞으면 판단을 포기하고 전부 붙인다 — 근거가 없는 것보다 많은 게 낫다.
리마인더에서 근거 항목은 뺐다(이제 불필요). calculate 항목만 남겼다.

**[2] 도구를 안 부르는 경로에도 검토를 한 번 넣는다.**
첫 응답에 `tool_calls` 가 없으면 `REVIEW` 를 붙여 한 번 더 부른다(플래그로 1회).
이 경로는 리마인더가 닿지 않아 거절 답변에 추측이 붙던 자리다.

**[3] planner 시점 규칙.** "질문에 연도가 명시되어 있으면 그 연도를 그대로
fiscal_year 로 쓴다. 최신 보고서를 찾으려 하지 마라."

### 검증 — 3질문 × 2회

| 실행 | 질문 | 도구 | calc | fiscal_year | 근거절 | 대괄호 | 추측 |
|---|---|---|---|---|---|---|---|
| s1a/s1b | 비교 | 3 | 1 | **2024** | 있음 | **2** | 없음 |
| s2a/s2b | 단일 값 | 1 | 0 | **2024** | 있음 | **1** | 없음 |
| s3a/s3b | 거절 | 0 | 0 | — | 없음(정상) | — | 일부 |

[1] 과 [3] 은 한 번에 해결됐다. 근거 절은 4/4 대괄호까지 정확하고,
비교 질문에서는 도구가 돌려준 7건 중 실제 인용한 2건만 골라 붙었다.
`fiscal_year` 는 6/6 모두 2024 다(이전엔 단일 값 질문이 2/2 로 2025 였다).

### [2] 는 세 번 만에 잡았다 — 프롬프트로는 안 됐다

| 시도 | 결과 |
|---|---|
| system.txt 에 "추측하지 마라" 두 줄 | 2/2 실패. 금지 문구를 그대로 씀 |
| REVIEW 재호출 | 추측은 줄었으나 **"죄송합니다. 수정된 답변은 다음과 같습니다"** 메타 대화가 노출 |
| REVIEW 에 "본문만 출력하라" 추가 | 메타 대화는 사라졌으나 **"근거: 상법 제391조에 따라…"** 로 라벨만 바꿔 추측 |

`drop_baseless_geun()` — 도구가 돌려준 출처가 **하나도 없으면** 본문에서

**배운 것.** 형식·금지 규칙은 프롬프트로 세 번 막아도 표현만 바꿔 가며 새어 나온다.
결정적으로 정할 수 있는 것은 코드에서 정하는 게 싸고 확실하다.

### "최근" 질문이 옛날 보고서를 물고 온 이유 (2026-09-02)

"LG이노텍 최근 사업 내용" 이 2024 사업보고서를 인용했다. 코퍼스에는 2025
사업보고서가 있는데도 그랬다. 프롬프트를 고치기 전에 원인부터 갈랐다.

**같은 질문을 세 번 돌렸다.** LLM 이 매번 다르게 움직여서 한 번으로는 못 가린다.

| 회차 | list_disclosures | search 인자 | 결과 |
|---|---|---|---|
| 1 | 안 부름 | fiscal_year=2025, **query 없음** | error → 재시도 없이 포기 |
| 2 | **불렀다**(limit=10) | rcept_no=20250318001384 | 2024 정정 사업보고서 |
| 3 | 안 부름 | fiscal_year=2025, query='사업보고서' | 2025 분기·반기보고서 |

#### 원인 1 — 목록 도구가 최신을 버리고 있었다

2회차가 결정적이었다. **모델은 시키는 대로 목록을 먼저 확인했다.** 추측하지
않았다. 그런데 `list_disclosures` 가 접수일 **오름차순**으로 정렬한 뒤
`limit` 으로 잘랐다. 오래된 것부터 10건을 주고 최신 7건을 버린 것이다.

LG이노텍 정기보고서 17건을 오래된 순으로 세면 10번째가 정확히
`20250318001384`([기재정정]사업보고서 2024.12)다. 모델이 본 목록에서 그게
"가장 최신" 이었다. 도구가 거짓말을 했고 모델은 그걸 믿었다.
2026년 문서(사업보고서 2025.12, 분기보고서 2026.03)는 아예 보이지 않았다.

프롬프트를 아무리 강하게 써도 이 버그가 남아 있으면 같은 답이 나온다.

#### 원인 2 — 검색어 "사업 내용" 두 단어가 증자현황 표에 걸린다

답변에 지분증권 발행 실적이 섞여 나온 건이 있었다. LLM 없이 검색기만 돌려
그대로 재현했다. `search_disclosure('사업 내용', corp_name='LG이노텍')` 의 1위가
"증권의 발행을 통한 자금조달 실적" 청크다.

그 청크 안에 증자현황 표가 있고 헤더가 이렇다 —
"발행(감소)한 주식의 **내용** 종류 / **내용** 수량 / **내용** 주당액면가액 /
**내용** 주당발행가액 / **내용** 비고". 한 청크에 `내용` 이 다섯 번 나온다.
질의어가 `사업`+`내용` 두 토큰뿐이라 이 반복이 BM25 점수를 그대로 가져갔다.

무관한 절이 딸려온 게 아니라 **질의어가 짧아서 표 헤더가 1위를 한 것**이다.
질의어를 "사업의 개요 주요 제품 광학솔루션 기판소재 전장부품" 으로 바꾸면
BM25 가 4 → 75 로 뛰고 지분증권은 사라진다.

#### 원인 3 — 연도를 명시해도 사업보고서를 못 고른다 (새로 발견)

"LG이노텍 2025년 사업 내용" 으로 물으면 `fiscal_year=2025` 는 정확히 들어간다.
그런데 인용된 3건이 전부 분기·반기보고서였다. 사업보고서(2025.12)는 한 건도 없다.

`fiscal_year=2025` 는 그 사업연도의 분기(03/09)·반기(06)·사업보고서(12)를
**전부** 포함한다. 좋은 질의어로 문서당 상한을 풀고 top10 을 봐도 사업보고서는 9위다.

| 문서 | 같은 절(II.사업의 내용 > 1.사업의 개요) BM25 |
|---|---|
| 분기보고서 (2025.09) | 75.40 |
| 분기보고서 (2025.03) | 74.39 |
| 사업보고서 (2025.12) | **48.91** |

같은 절인데 사업보고서만 낮다. 사업보고서의 청크가 더 길어서 BM25 길이
정규화에 손해를 본다. **`fiscal_year` 는 "사업보고서를 달라" 는 뜻이 아니다.**
연간 확정치를 원하면 문서를 `rcept_no` 로 못 박거나 보고서 종류를 지정해야 한다.

#### 고친 것 넷

**[1] `listing.py` 정렬을 내림차순으로.** `limit` 에 잘리는 쪽은 반드시 오래된
것이어야 한다. `series_of`(정정 이력)만 **자른 뒤에** 오름차순으로 되돌린다 —
정정 이력은 시간순이 읽기 좋고, 자른 뒤라 최신본이 사라지지 않는다.

**[2] `report_type` 인자를 새로 노출했다.** `annual`/`half`/`quarter`.
id_map 에 `doc_subtype` 이 이미 조인돼 있어 필터 한 줄만 추가하면 됐다.
한국어("사업보고서")로 와도 받는다.

**기본값은 "안 넣음" 이다.** 이게 중요하다. 모델이 습관적으로 넣기 시작하면
접수번호로 이미 특정된 문서에까지 종류를 붙여 0건을 만든다. 그래서 tools.json
설명을 단정형으로 쓰지 않았다 — "확신이 없으면 넣지 않는 쪽이 안전하다".
모르는 값이 오면 조용히 무시하지 않고 note 로 알린다(규칙 9).

**[3] planner `[시점 정규화]` 재작성 + `[보고서 종류 선택]` 신설.**
"최근/요즘/현재" 면 목록을 먼저 확인하고, 특정 문서를 봐야 하면 `fiscal_year`
가 아니라 `rcept_no` 를 넣는다. 고를 때는 `is_latest_in_series` 를 본다.

**[4] `query` 누락 시 안내.** 기본 질의어를 지어내지 않는다 — corp_name 으로
질의어를 만들면 검색은 되지만 무엇을 찾는지 아무도 모른다. 대신 error note 에
무엇이 빠졌는지와 예시를 넣고, system.txt 재시도 규칙에 `status="error"` 를
추가했다. 전에는 `not_found` 만 다뤄서 error 를 받은 모델이 그냥 포기했다.

### 골든셋 라벨링을 최우선에서 뺀다 (2026-09-02 결정)

`eval/golden_todo.jsonl` 30건 중 19건까지 라벨링하고 멈췄다. 나머지 11건은 안 한다.

**남은 11건의 구성**: `search_open` 10건 + `메리츠금융지주__multi_closed` 1건.

`search_open` 은 "이 회사가 뭘 만들어 파는지, 시장이 어땠는지, 앞으로 뭘 하겠다는
건지 정리해라" 같은 질문이다. 정답이 문서 여러 절에 걸친 종합 서술이라
**"이 청크가 정답" 이라고 찍을 수 있는 대상이 없다.** 청크 단위 정답이 정의되지
않으므로 recall 로 잴 수 없다. 실제로 라벨링을 시도한 5건이 5/5 부적합이었다.

**18건으로 이미 결론이 났다.** 지표가 두 덩어리로 깨끗하게 갈리고
(`found_by_grep` 7건 recall@20 0.286 / 그 외 11건 1.000), 7건의 원인도
단계 3-G 진단에서 (a) 검색어 문제 4건 / (b) 검색기 문제 3건으로 분해됐다.
색인 자체는 멀쩡하다는 것도 확인했다. 표본을 30건으로 늘려도 알게 될 것이 없다.

`search_open` 은 9/3 e2e 평가에서 **Agent 단위로** 본다. 서술형 답변의 품질은
청크가 올라왔는지가 아니라 답이 맞는지로 재는 게 맞다.

### e2e 평가에 돈 새는 것을 막는 장치를 먼저 달았다 (2026-09-02)

평가를 돌리기 전에 **얼마나 쓰는지 보이게** 만들었다. HyperCLOVA X 는 요금표를
확인하지 못했고(문서·상품 페이지 어디에도 단가가 없다), 한 번 잘못 돌리면
몇천 원이 조용히 나간다. 그래서 여섯 가지를 달았다.

**환산 기준.** 2,000,000 토큰 = 4,800원(사람이 정한 값). 0.0024원/토큰.
`src/agent/usage.py` 상수 둘만 고치면 바뀐다. 리포트에는 언제나 '추정' 이라고 적는다.

#### 1. 실행 전 예상치 — `--yes` 없으면 안 돈다

```
40문항 × 평균 50,000 토큰 예상 = 2,000,000 토큰 ≈ 4,800원
근거: 기본 가정 50,000토큰 — 실측 이력이 아직 없다
상한: 5,000원
실제 호출은 하지 않았다. 진행하려면 --yes 를 붙여라.
```

한 번이라도 돌린 뒤에는 `token_log.jsonl` 의 **실측 평균**으로 예상치를 낸다.
근거가 기본 가정인지 실측인지도 같이 찍는다.

#### 2. 상한 — 문항 경계가 아니라 LLM 호출 직전에 본다

`--max-cost`(기본 5,000원). 문항이 끝나기를 기다리면 그 문항 값은 이미 나간 뒤다.
그래서 `loop._run` 의 while 첫 줄에서 확인하고 **문항 중간에도** 멈춘다.
멈춘 사실은 `stopped_by_budget` 과 `note` 에 남고, 결과는 문항마다 곧바로
`eval/e2e_runs/<run>.jsonl` 에 append 되므로 `--resume` 으로 이어서 간다.

#### 3. usage 가 없는 호출을 0 으로 채우지 않는다

응답에 `usage` 가 없으면 토큰을 `null` 로 남기고 `unknown_calls` 로 따로 센다.
0 으로 채우면 **"안 썼다" 와 "모른다" 가 구분되지 않고** 예산이 조용히 샌다.
합계 옆에는 "이 값은 하한이다" 를 붙인다.

#### 4. 낭비 신호 넷

| 항목 | 무엇을 뜻하나 |
|---|---|
| 재호출 차단 | 같은 인자로 또 불렀다. 많으면 모델이 검색어를 안 바꾼다 |
| error/not_found 뒤 재시도 | 스스로 고쳐 다시 불렀다. 많으면 첫 검색어가 나쁘다 |
| 도구 6회 한도 도달 | 많으면 계획이 헤맨다 |
| 429 재시도 | 횟수와 대기 초 |

**429 의 낭비 토큰은 만들어 내지 않았다.** 요청이 거절된 것이라 usage 가 오지
않는다. 대신 "재시도가 같은 본문을 다시 보냈다" 는 사실만 `다시 보낸 프롬프트
토큰(추정)` 으로 남기고, 서버가 그것을 과금했는지는 알 수 없다고 적었다.

#### 5. 누적 로그 한 파일

`eval/token_log.jsonl` 에 호출 하나당 한 줄. `run_e2e` · `ask` · `quick_qa` 가
모두 같은 파일에 쓴다. `python eval/token_log.py --summary` 로 오늘/누적,
스크립트별·모델별·날짜별 분해를 본다.

가짜 LLM 으로 도는 테스트가 이 파일을 더럽히던 것을 잡았다 —
`usage.set_enabled(False)` 를 `test_loop.py` 와 `test_usage.py` 가 부른다.

#### 6. 검증 — `eval/test_usage.py`, LLM 호출 0회

가짜 `clova.chat` 으로 30개 항목을 확인했다. 전부 통과.
`test_loop` · `test_tools` · `test_context` · `test_recency` 도 통과.

**돌리면서 처음 안 것.** 도구를 한 번도 안 부르는 답변(거절 등)은 `loop` 가
`REVIEW` 로 한 번 더 부르기 때문에 **LLM 을 2회 쓴다.** 계측을 붙이기 전에는
안 보이던 비용이다. 거절 문항이 많으면 그만큼 더 든다.

#### 문항 적재 — 실제 240건

`benchmark_*.json` 43개 중 템플릿 파일 1개를 빼고, 내용이 같은 파일 쌍 2개를
하나로 합치면 **40개사 × 6유형 = 240문항**이다(HANDOFF 에 적힌 252 는 파일 수를
그대로 센 값으로 보인다). 표본은 유형이 고루 섞이게 돌아가며 뽑고 시드를 고정했다.

**채점은 아직 하지 않는다.** 자동 채점 방식이 정해지지 않아서, 답변과 정답을

`numbers_hit`(정답의 숫자가 답변에 몇 개 있는지)로 남겼고, 이것은 **점수가 아니라

### 단가를 실제 값으로 바꿨다 — 입력과 출력을 나눠서 센다 (2026-09-02)

앞 단계에서 "200만 토큰 = 4,800원" 이라는 **총 토큰 하나짜리 환산**을 썼다.
실제 HCX-005 단가를 확인받고 바꿨다.

| 구분 | 1,000토큰당 | 토큰당 |
|---|---|---|
| 입력(프롬프트) | 1.25원 | 0.00125원 |
| 출력(완성) | 5.00원 | 0.005원 |

**출력이 입력의 4배다.** 그래서 총 토큰 하나로 환산하면 안 된다. 같은 100만 토큰도
전부 입력이면 1,250원, 전부 출력이면 5,000원이다 — 4배 차이다.
`won(prompt, completion)` 이 둘을 따로 곱한다.

#### 둘 중 하나라도 모르면 금액을 내지 않는다

`usage` 에 내역이 없고 총 토큰만 있으면 `None` 을 돌려준다. 비율을 가정해서
채우면 그 추정이 **최대 4배 틀린다.** 앞 단계에서 "0 으로 채우지 않는다" 로
잡아 둔 것과 같은 이유인데, 단가가 갈리면서 훨씬 중요해졌다.
그런 호출은 `unknown_calls` 로 세고 합계 옆에 "하한" 이라고 붙인다.

#### 예상치가 바뀌었다 — 4,800원 → 3,250원

```
40문항 × 평균 입력 45,000 + 출력 5,000 토큰
  입력 1,800,000 토큰 → 2,250원
  출력   200,000 토큰 → 1,000원
  합계 2,000,000 토큰 ≈ 3,250원
```

문항당 5만 토큰이라는 총량 가정은 그대로 두고 입력 45,000 / 출력 5,000 으로
쪼갰다. 이 Agent 는 도구 결과를 프롬프트에 계속 쌓고(시스템 4,000자 + 턴마다
12,000자), 출력은 `loop.MAX_TOKENS=2048` 로 묶여 있어 9:1 쯤으로 봤다.
**이건 아직 가정이다** — 화면에 "가정" 이라고 찍고, 한 번 돌리면
`token_log.jsonl` 의 실측 평균으로 자동 대체된다.

#### 리포트가 입력·출력을 나눠 보여준다

`run_e2e` 리포트의 비용 표, 문항 상위 5(이제 **토큰 순이 아니라 비용 순**),
유형별 평균, `token_log.py --summary` 의 모든 표에 입력·출력 칸이 따로 있다.
출력이 4배 비싸므로 "토큰을 많이 쓴 문항" 과 "비용이 큰 문항" 이 다를 수 있어서
정렬 기준을 비용으로 바꿨다.

#### 검증 — `eval/test_usage.py`, LLM 호출 0회

단가 계산(입력 1.25 / 출력 5.00 / 4배 관계 / 내역 없으면 None), 예산,

#### numbers_hit 은 채점에 쓸 수 없다 — 이 실행으로 확정됐다

리포트의 "유형별 정확도 0%" 와 "작문 29건" 을 **그대로 읽으면 안 된다.**

있어 분모가 부풀려진다. 40문항에서 일치율이 0.5 를 넘은 것은 1건뿐이고
최고가 0.857 이다. 임계값 artifact 이지 성능 측정이 아니다.

객관적으로 믿을 수 있는 것은 **근거를 올렸는가(30/40)** 와 **도구 status** 뿐이다.
맞고 틀림은 `reports/e2e_v2_review.md` 를 사람이 읽어야 한다.

#### 그 밖에

- **HTTP 400 `40009 Unsupported function` 1건.** 미래에셋증권 complex_closed
  에서 첫 호출부터 400 이 왔다. 400 은 재시도 대상이 아니라 그대로 실패했고,
  루프는 계약대로 규격 dict 를 돌려줬다(토큰 0, `unknown_calls=1`).
  40문항 중 1건이라 원인은 아직 모른다
- **429 0회.** 문항 사이 20초로 충분했다(86회 호출)
- 예외로 죽은 문항 0건
- 입력:출력 = 97.1 : 2.9. 5문항 때(95.7:4.3)보다 출력 비중이 더 낮다

### 프롬프트 오염 제거 + 접수번호 방어 + 자동채점 폐기 (2026-09-02)

e2e 1차에서 나온 세 가지를 고쳤다.

#### [1] 프롬프트의 실제 접수번호를 자리표시자로

`prompts/system.txt` · `system_min.txt` 의 답변 예시에 실제 접수번호가 7군데씩
14개 있었다. 두산로보틱스 문항에서 모델이 KB금융 예시 번호 `20260619000667` 을
그대로 `series_of` 에 넣은 것이 확인됐다. **예시가 오염원이었다.**

```
[KB금융 [기재정정]사업보고서 …, 접수번호 20260619000667]
  → [△△지주 [기재정정]사업보고서 …, 접수번호 20260619XXXXXX]
[SK하이닉스 사업보고서 …, 접수번호 20250311001275]
  → [○○기업 사업보고서 …, 접수번호 20250311XXXXXX]
```

회사명도 실존 조합을 피했다(○○기업 / △△지주). 접수번호는 앞 8자리(날짜)만 남기고
일련번호를 `XXXXXX` 로 가렸다 — 형식은 배우되 베낄 값은 없다.
예시 절 머리에 "이 값들은 자리표시자다" 를 한 문단 넣었다.
`planner.txt` · `tools.json` 에는 원래 없었다(전량 검색으로 확인).

베껴 써도 이제 도구가 "14자리 숫자여야 한다" 로 잡아낸다 — 이중 방어다.

#### [2] list_disclosures / search_disclosure 방어 셋

전에는 무엇을 잘못했든 "조건에 맞는 공시가 없다" 한 줄이었다. 모델이 고칠 수가 없다.
이제 이유와 **고치는 법**을 같이 준다.

| 경우 | status | note |
|---|---|---|
| 앵커 문서 회사 ≠ corp_name | error | `series_of=… 는 KB금융 의 문서다. 두산로보틱스 의 질문에는 쓸 수 없다. 먼저 list_disclosures(corp_name=…) 로 …` |
| 코퍼스 범위 밖 연도 | not_found | `코퍼스는 2023~2026년 공시만 담고 있다. fiscal_year=2017 은 범위 밖이다` |
| 없는 접수번호 | error | `접수번호 … 이 코퍼스에 없다. 접수번호를 추측하지 말고 …` |
| 14자리가 아님 | error | `… 는 형식이 틀렸다 — 14자리 숫자여야 한다. …` |

연도 범위는 **상수로 박지 않고 manifest 에서 구한다**(`fiscal_span()`).
데이터가 바뀌면 안내 문구도 같이 바뀌어야 한다.
접수번호 검사는 `listing.rcept_problem()` **한 곳**에서만 판단하고
`search_disclosure` 도 그것을 쓴다 — 두 곳에서 따로 판단하면 안내가 갈리고,
갈린 안내는 모델이 못 고친다.

#### [3] planner 두 줄

접수번호를 조립하지 마라(날짜+000001 은 틀린다), 코퍼스는 2023~2026 뿐이다.

#### [4] 자동 채점 폐기

`numbers_hit` 을 없앴다. 정답에 `※ 오답 유형: … 를 답하면 오답` 형태의 반례
숫자가 섞여 분모가 부풀려져서, 40문항에서 일치율 0.5 초과가 1건뿐이었다.
그걸로 "정확도 0%" 를 적는 것은 측정이 아니라 거짓말이다.

리포트에서 "정확도" 를 빼고 **기계가 틀림없이 아는 것**만 남겼다 —
근거 확보율(30/40 = 75%), 도구별 성적, 타사 출처 인용, 거절 횟수.
3분류도 근거를 못 올린 문항만 검색/계획으로 가르고, 근거가 있는 30건은
`보류(사람)` 로 넘긴다. 작문 문제는 사람이 읽어야 갈린다.

`reports/e2e_v2_review.md` 를 판정용으로 다시 만들었다.
정답(핵심)과 Agent 답변을 **HTML 두 칸 표로 나란히** 놓아 스크롤 없이 비교되게 하고,
`※ 오답 유형` 이후는 문항 끝 `<details>` 로 접었다. 문항마다 판정란을 뒀다.

  판정 — [정답: O / X / 부분]  [출처: O / X]  [환각: O / X]  [메모: ]

#### 검증 — LLM 호출 0회

`cited_other_corp` · `refusal_count` 를 검사한다. 5개 테스트 전부 통과.

```
두산로보틱스   series_of="20260619XXXXXX"   ← 프롬프트 예시를 그대로
LG유플러스     series_of="20240306XXXXXX"

받고 재시도 없이 포기한 OCI홀딩스다.

두산퓨얼셀이 정확히 그 조합으로 죽었다(exchange 문서 83건을 갖고 있는데도).
도구는 "조건에 맞는 공시가 없다" 라고만 답해 이유를 안 알려줬다.

했으나 **다섯 조건 모두에서 안 죽었다** — 평범한 로드, `HF_HUB_OFFLINE=1`,
백그라운드 스레드, 프로세스 2개 동시(각 2.8GB, 합계 5.6GB). 지금 GPU0 은 0MiB
사용에 24GB 여유, RAM 385GB 여유, 경쟁 프로세스 없음이다.

재현은 못 했지만 **죽을 수 있는 자리 네 곳**을 찾아 막았다.

#### 1. 모델을 매번 huggingface.co 에서 확인하고 있었다

`paths.MODEL_NAME` 은 `"BAAI/bge-m3"`, 로컬 경로가 아니라 저장소 id 다.
기동할 때마다 `Fetching 30 files` 로 네트워크를 친다. 지금 도는 이유는
`~/.cache/huggingface/hub` 에 4.59GB 가 이미 있어서일 뿐이다.

`src/search/hf_cache.py` 를 만들어 `_load_model()` 직전에 부른다.
**캐시를 먼저 확인하고, 있을 때만 `HF_HUB_OFFLINE=1` 을 건다.** 없는데 걸면
받을 길이 막히므로 순서가 중요하다. 없으면 조용히 멈추지 않고 경로와 고치는 법을
적어 `SystemExit` 로 죽는다.

환경변수를 늦게 걸면 안 먹는 함정이 있다 — `huggingface_hub.constants.HF_HUB_OFFLINE`
은 import 할 때 한 번만 읽힌다. 이미 올라와 있으면 모듈 속성까지 같이 바꾼다.

#### 2. 이 PC 는 부팅할 때 MITM 프록시가 뜬다

시작프로그램 폴더의 `start_proxy.bat` 이 `mitmdump --listen-port 3128` 을 띄운다
(2025-07-01 등록, 이 프로젝트와 무관). 지금은 `HTTPS_PROXY` 가 안 잡혀 있어
무해하지만, 잡히는 순간 HF 가 TLS 검증에 실패해 **모델 초기화에서 죽는다** —
증상이 정확히 일치한다.

`scripts/serve.bat` 이 기동 때 프록시 변수를 **명시적으로 비운다**.
남이 잡아 둔 값이 상속되지 않게.

#### 3. gpu_guard 가 항상 0번에 상한을 걸고 있었다

`apply_memory_fraction(physical, ...)` 이 인자를 무시하고
`set_per_process_memory_fraction(fraction, 0)` 이었다. `select_gpu()` 를 먼저 부르는
경로에서는 `CUDA_VISIBLE_DEVICES` 로 한 장만 보여 0 이 맞다. 그런데
`src/search/hybrid.py` 는 `select_gpu` 를 안 거치므로 `gpu=1` 을 줘도 0번에 걸렸다.

`torch_index()` 를 새로 두어 두 경우를 구분한다 —
`CUDA_VISIBLE_DEVICES` 가 있으면 그 목록에서의 위치, 없으면 물리 번호가 곧 인덱스.

**남은 문제(안 고침)**: `hybrid` 는 dense 를 언제나 문자열 `"cuda"`(= 0번)에 올린다.
`Retriever(gpu=1)` 을 줘도 데이터는 0번으로 간다 — `gpu` 인자가 사실상 장식이다.
마감 이틀 전이라 배치 로직은 건드리지 않고 기록만 남긴다.

#### 4. 두 벌 로드

`Retriever()` 를 직접 만들고 `get_searcher()` 도 부르면 인덱스와 모델이 통째로
두 벌 올라간다(실측 GPU 1.26 → 2.52GB). `_INSTANCE` 가 아니라 **만든 횟수**를 세서
두 번째부터 경고한다 — 직접 만든 뒤 `get_searcher()` 를 부르는 순서에서는
그 시점 `_INSTANCE` 가 아직 None 이라 못 잡는다.

직접 만드는 곳은 전부 일회성 CLI 다(`label_helper` `quick_qa` `run_eval`
`show_chunks` `test_retriever`). 한 프로세스에서 둘을 섞는 코드는 없어서
지금 당장 이중 로드가 나지는 않는다. 스크립트는 건드리지 않았다.

#### 기동 전 점검 — `scripts/preflight.py`

인덱스를 올리지 않고 1초 안에 끝난다. 프록시 변수 / 모델 캐시 / 인덱스 파일 /
GPU 여유 / API 키 다섯 가지를 보고 막힌 것이 있으면 **고치는 법과 함께** 1 로 죽는다.
`scripts/serve.bat` 이 서버를 띄우기 전에 이걸 먼저 통과시킨다.

`--warmup` 을 붙이면 실제로 35초 올려 본다.
