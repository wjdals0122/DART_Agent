`docs/WORKLOG.md` 는 시간 순 누적 기록이라 길다. 이 문서는 **주제별로 접은 요약**이다.

## 1. 이 기간에 만든 것

### 1-A. 토큰·비용 회계 (`src/agent/usage.py`, `eval/token_log.py`)

평가를 돌리기 전에 **얼마나 쓰는지 보이게** 만들었다.

```
usage.set_context(script="run_e2e", qid="...")   # 이 호출이 어디서 났는지
usage.use_budget(usage.Budget(limit_won=5000))   # 상한
usage.record(model=..., usage_dict=res["usage"]) # 호출 1건 = 로그 1줄
```

- **단가**: 입력 1,000토큰 1.25원 / 출력 1,000토큰 5.00원 (HCX-005)
- 모든 LLM 호출이 `eval/token_log.jsonl` 한 파일에 쌓인다 (`run_e2e`·`ask`·`quick_qa` 공용)
- `python eval/token_log.py --summary` 로 오늘/누적·스크립트별·모델별 분해

### 1-B. e2e 평가 러너 (`eval/run_e2e.py`)

벤치 문항을 Agent 에 끝에서 끝까지 태운다.

```
python eval/run_e2e.py --n 40                        # 예상 비용만 (LLM 안 부름)
python eval/run_e2e.py --n 40 --yes --max-cost 3000  # 실행
python eval/run_e2e.py --run <이름> --resume --yes    # 중단 지점부터
```

- 문항 240건 (40개사 × 6유형). 표본 40건은 `eval/e2e_sample.jsonl` 에 **고정**
- 결과는 문항마다 곧바로 append → 죽어도 거기까지는 남는다
- 리포트 `reports/<run>.md` + 사람 채점용 `reports/<run>_review.md`

## 2. 안전장치 — 돈이 새지 않게

| 장치 | 동작 |
|---|---|
| 실행 전 예상치 | `--yes` 없으면 예상 비용만 찍고 **종료**. 실측 이력이 있으면 그 평균을 쓴다 |
| 비용 상한 | `--max-cost`(기본 5,000원). **LLM 호출 직전**에 확인 → 문항 중간에도 멈춘다 |
| 이어가기 | `--resume` 이 끝낸 문항을 건너뛴다 (5→0건, 40→35건 확인) |
| 고정 표본 | 실행마다 표본이 바뀌면 앞뒤 비교가 불가능하다 |
| 테스트 격리 | `usage.set_enabled(False)` — 가짜 LLM 테스트가 비용 로그를 더럽히지 않는다 |

| 5문항 스모크 | 5 | 112원 | 214초 |
| 40문항 전량 | 40 | **599원** | 1,407초 |

## 3. 발견한 문제와 고친 방법

### 3-A. "최근" 질문이 옛 보고서를 물었다 → **도구가 거짓말을 하고 있었다**

**증상.** "LG이노텍 최근 사업 내용" 이 2024 사업보고서를 인용. 2025 것이 있는데도.

**진단.** 같은 질문을 3회 돌렸다(LLM 이 비결정적이라 1회로는 못 가린다).
2회차에서 모델이 **시키는 대로 `list_disclosures` 를 먼저 불렀다.** 추측하지 않았다.
그런데 그 도구가 접수일 **오름차순**으로 정렬한 뒤 `limit` 으로 잘랐다 —
오래된 것부터 10건을 주고 최신 7건을 버렸다. LG이노텍 정기보고서 17건을
오래된 순으로 세면 10번째가 정확히 그 2024 정정본이다.

**고침.** 정렬을 내림차순으로. `series_of`(정정 이력)만 **자른 뒤** 시간순으로 되돌린다.

**배운 것.** 프롬프트가 안 지켜지는 것처럼 보일 때 모델을 먼저 의심하면 틀린다.

### 3-B. `fiscal_year` 는 "사업보고서를 달라"는 뜻이 아니다

같은 사업연도의 분기(03/09)·반기(06)·사업보고서(12)를 **전부** 포함한다.
게다가 사업보고서 청크가 더 길어 BM25 길이 정규화에 손해를 본다
(같은 절: 분기 75.4 vs 사업보고서 48.9). → `report_type`(annual/half/quarter) 신설.
**기본은 안 넣는다** — 접수번호로 이미 특정된 문서에 붙이면 0건이 된다.

### 3-C. 검색어 "사업 내용" 두 단어가 증자현황 표에 걸렸다

LLM 없이 재현: `search_disclosure("사업 내용", corp_name="LG이노텍")` 1위가
**지분증권 발행 실적** 청크. 그 청크의 증자현황 표 헤더에 `내용` 이 5번 나온다
("주식의 **내용** 종류 / **내용** 수량 / …"). 질의어가 2토큰뿐이라 반복이 BM25 를 먹었다.
→ planner 에 "절 제목 일반어만으로 검색하지 마라" 한 줄.

### 3-D. 도구 error 를 받으면 답변을 포기했다

`search_disclosure` 를 `query` 없이 부르고 error 를 받자 재시도 없이 거절.
system.txt 의 재시도 규칙이 `not_found` 만 다뤘다.
→ `status="error"` 도 포함 + error note 에 **무엇이 빠졌는지와 예시**를 넣었다.
기본 질의어를 지어내지는 않았다 — 무엇을 찾는지 아무도 모르는 답이 나간다.

### 3-E. 벤치 문항 200/240(83%)이 회사명을 안 적는다 → **하네스 결함**

**증상.** 첫 5문항에서 3건이 근거 0건. OCI홀딩스 문항 답변이 **롯데케미칼**을 찾고 있었다.

**진단.** 질문 원문에 회사 이름이 없다. 벤치는 `doc_info` 로 **대상 문서가 이미
정해진 상태**를 전제하고 쓰였는데(`"이 보고서"`, `"이 회사"`), 러너가 `query` 만
넘기고 `doc_info` 를 버렸다. 회사를 모르는 질문을 던져 놓고 Agent 실패로 적고 있었다.

| 유형 | 회사명 없음 |
|---|---|
| search_closed · multi_open | **40/40** |
| complex_closed | 39/40 |
| complex_open · multi_closed | 37/40 |
| search_open | 15/40 |

**고침.** 회사명만 주입(`"{회사}에 대해 묻습니다. "`). `doc_info` 의 접수번호는
주지 않는다 — 문서 탐색은 Agent 몫으로 남겨야 검색을 평가할 수 있다.
조사를 붙여 주어에 녹이는 방식은 첫 어절 품사가 문항마다 달라 뜻이 바뀔 위험이 있어 안 썼다.
전후 전량은 `reports/e2e_question_rewrite.md`.

### 3-F. 프롬프트 예시의 실제 접수번호를 베꼈다

**증상.** 두산로보틱스 문항에서 `series_of=20260619000667`.
이건 `prompts/system.txt` 의 **KB금융 예시 접수번호**다.
도구는 정직하게 "계열 기준: KB금융" 이라고 답했는데 모델은 두산로보틱스 자료로 취급했다.

**고침.** 실제 값 14개를 자리표시자로(`20260619XXXXXX`), 회사명도 실존 조합 회피
(`○○기업` / `△△지주`). 예시 절 머리에 "이 값들은 자리표시자다" 문단 추가.

**부작용과 이중 방어.** 다음 실행에서 이번엔 **자리표시자를 베꼈다**
(`20260619XXXXXX`, `000001`). 하지만 도구가 "14자리 숫자여야 한다"로 잡아냈고
**3건 모두 다음 호출에서 고쳤다.** 오염원 제거 + 형식 검증이 함께 작동했다.

### 3-G. 도구가 "없다" 고만 답해 모델이 못 고쳤다

접수번호를 지어내거나(날짜+`000001` 조립, 13자리) 범위 밖 연도를 넣어도
`"조건에 맞는 공시가 없다"` 한 줄뿐이었다.

**고침 — 이유와 고치는 법을 같이 준다.**

| 경우 | status | note |
|---|---|---|
| 앵커 회사 ≠ corp_name | error | `series_of=… 는 KB금융 의 문서다. 두산로보틱스 의 질문에는 쓸 수 없다. 먼저 …` |
| 코퍼스 범위 밖 연도 | not_found | `코퍼스는 2023~2026년 공시만 담고 있다` |
| 없는 접수번호 | error | `접수번호를 추측하지 말고 list_disclosures(corp_name=…) 로 …` |
| 14자리 아님 | error | `형식이 틀렸다 — 14자리 숫자여야 한다` |
| 사업연도 없는 doc_group + fiscal_year | error | `exchange 문서는 사업연도가 없다. date_from/date_to 를 쓰라` |
| 그 회사가 그 종류 0건 | not_found | `미래에셋증권 은 exchange 문서가 없다. 보유 현황: holding 11 / major 8 / periodic 19` |

**연도 범위·그룹 목록은 상수로 박지 않고 manifest 에서 구한다.**
데이터가 바뀌면 안내도 같이 바뀌어야 한다.

### 3-H. 사업연도는 periodic 에만 있다 (실측)

| doc_group | 문서 | 사업연도 있음 |
|---|---|---|
| periodic | 1,054 | **100%** |
| exchange | 1,469 | 0% |
| major | 598 | 0% |
| holding | 1,083 | 0% |

`report_nm` 이 `단일판매ㆍ공급계약체결` 처럼 `(YYYY.MM)` 을 안 달기 때문이다.
→ `doc_group="exchange" + fiscal_year` 는 **구조적으로 항상 0건**이었다.

### 3-I. 목록만 보고 답했다 — 최대 병목이었다

complex_closed 7건 중 3건이 `list_disclosures` 로 목록만 받고
`search_disclosure` 를 **한 번도 안 부르고** 답으로 갔다(두산로보틱스 34건, LG유플러스 4건).

**고침.** 성공 응답 note 에 매번 붙인다 —
`"이것은 문서 목록이며 내용이 아니다. rcept_no 를 골라 search_disclosure 를 호출하라"`.
프롬프트에만 적으면 도구 결과가 쌓일수록 멀어져 잊힌다. planner 에도 같은 규칙.

**효과: `search_disclosure` 호출 2회 → 14회, 근거 확보 1/7 → 4/7.**

### 3-J. 도구 0회 거절 · 타사 데이터 인용

- 두산에너빌리티 문항에서 **도구를 한 번도 안 부르고** "확인되지 않음" 을 냈다
- 미래에셋증권 문항에서 회사를 모르자 **SK하이닉스를 임의로 골라** 검색하고 그 회사
  데이터로 해외법인 순이익을 지어냈다(`676백만원` 7회 반복)

**고침.** `loop.py` 에 `FORCE_TOOL` — 첫 응답에 tool_calls 가 없고 아직 도구를
안 불렀으면 "조회부터 하라"를 한 번 붙여 되돌린다(그래도 안 부르면 진행).
system.txt 에 "회사가 불확실하면 임의로 고르지 말고 되묻는다",
"검색 결과의 회사명이 질문의 회사와 다르면 근거로 쓰지 마라".

**효과(5문항→40문항): 도구 0회 1/5 → 0/40, 타사 인용 1/5 → 0/40.**
`FORCE_TOOL` 은 발동 0회였다 — 회사명이 들어가자 처음부터 도구를 불렀다.

### 3-K. 근거 0건인데 수치를 단정했다

HD현대중공업이 도구가 **전부 not_found** 인 상태에서
"변경공시는 없었습니다. 확정된 계약 금액 총액은 **1,287십억 원**입니다" 를 냈다.
정답은 193,700백만원. 환각이다.

**고침 — 지우지 않고 표시만 한다.** 근거 0건 + (3자리 이상 숫자 또는 사실 단정 어미)면
답변 맨 앞에 `※ 아래 내용은 공시 조회로 확인되지 않았습니다.` 를 붙이고
`unsourced_claim=True` 로 집계한다. **거절 문장은 먼저 걷어낸다** —
안 그러면 정상 거절까지 오염 표시를 받는다.

지우지 않는 이유: 지우면 맞는 답도 잃는다. 표시하면 평가자가 판단할 수 있고
우리도 몇 건인지 셀 수 있다.

### 3-L. 자동 채점(`numbers_hit`)을 폐기했다

정답의 숫자가 답변에 몇 개 있는지 세는 방식을 잠정 채점으로 썼다.
40문항을 돌려 보고 **못 쓴다는 것이 확정**됐다 — 정답 문자열에
`※ 오답 유형: … 를 답하면 오답` 형태의 **반례 숫자**가 잔뜩 섞여 분모가 부풀려진다.
일치율 0.5 초과가 1건, 최고 0.857.

그걸로 "정확도 0%" 를 적는 것은 측정이 아니라 거짓말이다.
리포트에서 "정확도" 를 빼고 **기계가 틀림없이 아는 것**만 남겼다 —
근거 확보율 · 도구별 성적 · 타사 출처 인용 · 거절 횟수.
맞고 틀림은 `reports/<run>_review.md` 를 사람이 판정한다
(정답 핵심과 답변을 두 칸 표로 나란히, 오답 유형은 접어서 뒤로).

## 4. complex_closed 3회 실행 — 병목이 옮겨간 자취

이 유형만 `list_disclosures` 에 기댄다. 세 번 돌리며 병목이 한 칸씩 뒤로 갔다.

| | 1차 | 2차 | 3차 |
|---|---|---|---|
| 근거 확보 | 0/7 | 1/7 | **4/7** |
| `search_disclosure` | 2회 (0 ok) | 2회 (2 ok) | **14회 (8 ok)** |
| `list_disclosures` | 9회 (3 ok) | 13회 (4 ok) | 18회 (9 ok) |
| 접수번호 지어내기 | 4건 | 0건 | 0건 |
| 6회 한도 도달 | 0 | 0 | **2건** |
| 비용 | 57원 | 104원 | 174원 |

```
1차 병목: 접수번호를 지어낸다 · 프롬프트 예시를 베낀다
   ↓ (오염원 제거 + 형식/존재 검증)
2차 병목: 목록만 받고 본문을 안 연다
   ↓ (목록 note 에 다음 단계 안내 + planner 규칙)
3차 병목: 문서를 하나로 못 고른다 · 6회 한도가 정답 문서를 막았다
```

**3차의 결정적 장면.** HD현대일렉트릭이 exchange 목록 15건을 받고
접수번호를 하나씩 넣어 브루트포스로 뒤졌다. 한 턴에 toolCall 10개를 뿜었다.

```
[3] 20260106800025 → ok        [7] 20250225800764 → 호출 한도 초과   ← 정답 문서
[4] 20251222800814 → ok        [8]~[12] 전부 한도 초과
[5] 20250922800089 → ok
[6] 20250731800031 → ok
```

정답 문서가 정확히 7번째였다. **한 칸 차이로 잘렸다.**

## 5. 지금 남아 있는 문제

### 5-A. 문서를 하나로 특정하지 못한다 (가장 큼)

회사·기간까지는 맞게 좁히는데, 여러 후보 중 질문이 가리키는 문서를 못 고른다.
계약명(`"MGC 2척"`, `"362kV 고압차단기"`)으로 좁히는 단계가 없다.

| 문항 | 근거로 단 문서 | 문제 |
|---|---|---|
| HD현대일렉트릭 | 2026-01-06 계약 | 다른 계약 건. 정답 문서는 한도에 막힘 |
| HD현대중공업 | 2023-08-21 계약 | 질문은 **3월 10일** 건 |
| 두산로보틱스 | 주요사항보고서(타법인주식양수) | 질문은 「XI. 공시내용 진행 및 변경사항」 |

→ 접수번호를 하나씩 찍지 말고 `search_disclosure(query="MGC 2척 계약금액", doc_group="exchange")`
로 **본문 검색이 문서를 고르게** 하면 6회 한도 소진 문제도 같이 풀린다.

### 5-B. 6회 한도

한 턴에 toolCall 이 여러 개 오면 `n_calls` 가 한도를 넘어서까지 기록된다
(실제 실행은 6회까지, 나머지는 error 로 차단). 낭비는 없지만
**정답에 닿기 전에 예산이 소진되는 패턴**이 생겼다.

### 5-C. 정정 전 열 오독

HD현대일렉트릭이 정정본을 근거로 달고 정정 전 수치(583억·2026-01-30)를 읽었다.
벤치가 "오답(정정 전 수치)" 이라고 콕 집어 지목한 값이다.
system.txt 에 "정정 후 열을 쓴다" 를 넣었지만 3차에서는 다른 문서를 봐서 확인되지 않았다.

### 5-D. 무근거 표시의 한계

OCI홀딩스가 목록 59건만 보고 "2020년 5월 9일 … 언급될 가능성이 있음" 처럼
추측을 서술했는데 표시가 안 붙었다. 숫자가 연도뿐이라 제외 규칙에 걸렸다.

### 5-E. 채점이 아직 없다

`reports/e2e_v2_review.md`(40건) · `e2e_v4_cc_review.md`(7건)이 판정 대기 중이다.
자동 채점을 폐기했으므로 **유형별 정답률은 사람이 채워야 나온다.**

### 5-F. 확인되지 않은 것

- HTTP 400 `40009 Unsupported function` 1건 (40문항 중 1건, 원인 미상)
- 429 는 0회였다 — 문항 사이 20초로 충분(86회 호출)

## 6. 되돌리지 말 것

| 무엇 | 왜 |
|---|---|
| `list_disclosures` 최신순 정렬 | 오름차순으로 자르면 최신이 통째로 사라진다 |
| 목록 note 의 "내용이 아니다" 안내 | 프롬프트에만 적으면 도구 결과에 묻혀 잊힌다 |
| 접수번호 검증을 `rcept_problem()` 한 곳에서 | 두 곳에서 판단하면 안내가 갈리고, 갈린 안내는 모델이 못 고친다 |
| 프롬프트 예시의 자리표시자 | 실제 값을 두면 베낀다 (실측) |
| `usage` 결측을 0 으로 안 채움 | "안 썼다" 와 "모른다" 를 섞으면 예산이 조용히 샌다 |
| 입력·출력 단가 분리 | 출력이 4배 비싸다. 총 토큰 하나로 환산하면 최대 4배 틀린다 |
| 무근거 답변을 지우지 않고 표시만 | 지우면 맞는 답도 잃는다 |

## 7. 이 기간에 반복해서 확인된 것

1. **형식·금지 규칙은 프롬프트로 못 막는다.** 근거 절, 거절 답변의 추측,
   도구 0회 답변 — 전부 코드로 옮겨야 해결됐다.
2. **도구 결과에 실은 안내가 프롬프트보다 강하다.** 도구 결과가 12,000자씩 쌓이면
   시스템 프롬프트는 멀어진다. 고칠 지점 바로 옆에서 말해야 먹힌다.
3. **모델을 먼저 의심하면 틀린다.** "최근" 사건도, 87% 회사명 누락도,
   원인은 도구와 하네스였다.
4. **한 번 돌려서는 못 가린다.** LLM 이 비결정적이라 같은 질문에서 3가지 경로가 나왔다.
5. **못 재는 것을 재는 척하면 안 된다.** `numbers_hit` 폐기가 그 예다.
