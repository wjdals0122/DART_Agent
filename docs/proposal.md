# 기술 제안서 — DART 공시 질의응답 Agent

제10회 미래에셋증권 AI Festival · 팀 인천 · dis-044
End-point: **http://49.50.141.125** ([API 명세](API.md))

> **이 문서의 숫자는 전부 실측이다.** 각 숫자 뒤 대괄호가 출처다.
> 측정하지 않은 성능은 적지 않았고, 측정했으나 나빴던 것도 그대로 적었다.

## 1. 문제 정의와 접근

### 1.1 문제

DART 공시 코퍼스(70개사 · 4,204문서 · 2023.01~2026.03)[^m]에 대해 자연어 질문을
받아 **근거와 함께** 답한다. 외부 데이터는 쓸 수 없다(뉴스·리포트·위키·OpenDART
실시간 호출 금지). LLM은 HyperCLOVA X만 쓴다.

공시 질의응답이 일반 RAG와 다른 점 셋을 설계의 출발점으로 삼았다.

1. **회사·연도가 틀리면 답 전체가 틀린다.** "삼성전자 2024년 매출"에서 회사나
   연도가 어긋나면 아무리 유창한 답도 0점이다. 의미 유사도로 좁힐 문제가 아니라
   **메타데이터로 잘라야 할 문제**다.
2. **같은 문서가 여러 판 존재한다.** 4,204문서 중 **1,004건이 정정공시**다[^m].
   정정 전 값을 답하면 오답이다.
3. **답이 표 안에 있다.** 표 제목·단위·본문이 서로 다른 청크로 갈리면 LLM이
   단위를 추측한다. 실제로 백만원 표를 십억원으로 읽어 1,000배 틀린 적이 있다[^h].

### 1.2 접근

```
질문
 └─ 질문 재작성 (회사·회계연도·하위질문 추출)
     └─ HyperCLOVA X function calling 루프 (도구 5종 · 최대 6회)
         ├─ 하이브리드 검색 (하드필터 → BM25 + dense → RRF)
         ├─ 계산 (ast 화이트리스트)
         └─ 공시 목록·회사명 해석·진행표 조회
     └─ 최종 답변 검문 8종 → 되돌림 방어 → 후처리
 └─ 5필드 JSON (question_id · question · retrieved_context · think_trace · answer)
```

핵심 선택은 **"검색을 LLM에게 맡기지 않는다"** 다. 회사·연도·문서종류는 LLM이
자연어로 표현하되 검색기는 그것을 **필터 파라미터**로 받아 후보를 먼저 자르고,
그 안에서만 점수를 낸다. 회사명을 질의 문자열에 섞지 않는 이유이기도 하다.

## 2. 데이터 처리

### 2.1 코퍼스

| 구분 | 값 |
|---|---|
| 회사 | 70개사[^m] |
| 문서 | 4,204건[^m] |
| 기간 | 2023.01 ~ 2026.03 |
| 정정공시 | **1,004건**[^m] |
| 청크 | **614,578**[^lm] |
| 임베딩 | bge-m3 1024차원 dense (2.5GB fp32) + lexical sparse |

공시 유형별 분포[^m]:

| doc_group | 문서 수 | 내용 |
|---|---|---|
| exchange | 1,469 | 거래소공시 (단일판매·공급계약, 신규시설투자) |
| holding | 1,083 | 지분공시 (5% 보고) |
| periodic | 1,054 | 정기보고서 (사업 291 · 반기 234 · 분기 529) |
| major | 598 | 주요사항보고서 (증자·분할·자기주식) |

### 2.2 파싱 → 청킹

XML을 `lxml`로 파싱해 문서 JSON으로 만들고, 표를 마크다운 표로 렌더링한 뒤
절(section) 경로를 유지한 채 자족적인 청크로 자른다. 파싱·정규화층
(`src/normalize/` · `src/extract/` · `src/render/`)이 인코딩·표·기간·재무
표기를 공통으로 처리한다.

**표를 다루는 것이 이 단계의 전부였다.** 전량 조사 결과 청크의 **58.9%가 제목
없이 곧바로 표 행으로 시작**하고, **2.8%는 제목만 있고 표는 다음 청크에 있었다**[^hy].
그래서 검색 결과를 돌려줄 때 인접 청크에서 **단위·제목 줄만** 좁은 규칙으로
끌어와 붙인다(`_augment`). 앞뒤를 무조건 붙이면 남의 표 단위가 섞여 더 나빠지므로,
"표로 시작하고 단위 표기가 없을 때만" · "doc_id 경계를 넘지 않는다" 로 제한했다.

### 2.3 정정공시 마스킹

`manifest.is_correction` 으로 거르면 **정확히 반대로 작동한다** — 정정본이
최신본이기 때문이다. 그래서 별도의 마스크를 만든다[^lm].

| 항목 | 값 |
|---|---|
| 정기보고서 계열 | 897개 |
| 그중 정정이 있는 계열 | **135개** |
| 구본으로 밀려난 행 | 123,739 |
| 검색에서 제외한 행 | **97,223** |
| 보존한 행(`preserved`) | 26,516 |
| 검색 대상 행 | **517,355** |

`preserved` 는 정정본에 재수록되지 않은 구본 첨부(감사보고서·첨부재무제표)다.
통째로 버리면 그 절의 근거가 사라지므로 남기되, **같은 계열의 최신본이 더 위
순위에 이미 뽑혔을 때만** 버린다. "무조건 버린다"로 하면 감사의견 질의에서
1~4위 근거가 전부 사라지는 것을 실측으로 확인했다[^hy].

### 2.4 기수 → 연도 환산 (`doc_fiscal_map`)

공시는 "제56기"처럼 기수로 쓰고 질문은 "2024년"으로 묻는다.
처음에는 청크 안의 최대 기수를 당기로 보는 규칙을 썼는데 **21.8%가 틀렸다**[^h].
문서 단위 표(`{doc_id: {current_ki, fiscal_year, rcept_no}}`)로 바꿔 0.0%가 됐다.
70개사 전부 연결되고 ki→연도 충돌은 0건이다[^s39].

### 2.5 행 순서 계약

`chunks.jsonl` 행 = `dense.f32.npy` 행 = `id_map.parquet` 행 = BM25 행.
**어느 단계에서도 정렬·재배치하지 않는다.** 순서가 필요하면 인덱스 배열만 다룬다.
`verify_vectors` 가 행 수·shape를 대조하고 하나라도 다르면 멈춘다.
이 계약이 있어서 벡터·희소·원문·메타를 각각 다른 파일로 두고도 벡터 DB 없이
numpy memmap + scipy CSC + parquet만으로 돌린다.

## 3. 검색

### 3.1 구조 — 하드필터가 먼저다

```
필터(회사·사업연도·공시유형·접수번호·기간) → 후보 행 집합
  → BM25 점수 (후보에 대해서만)
  → dense 코사인 (후보에 대해서만)
  → RRF 융합 (각 리스트 top-200 안에 든 것만 기여)
  → 문서당 상한 → sha1 중복 제거 → preserved 조건부 드롭 → top-k
```

전체에서 top-k를 뽑고 나중에 거르는 흔한 구조를 **쓰지 않았다.** 회사 하나로
좁혔을 때 0건이 되기 때문이다. BM25도 라이브러리(`bm25s`·`rank_bm25`·
Elasticsearch)를 쓰지 않고 scipy CSC로 직접 구현했다 — 라이브러리는 전역 top-k를
전제하므로 하드필터 우선 구조에서 그 전제가 깨진다.

주요 상수: `RRF_K=60` · `TOP_M=200` · `POOL=50` · `w_vec:w_bm25 = 1:1`.

### 3.2 문서당 상한을 후보 문서 수에 맞춘다

상한이 2로 고정이면 후보 문서가 적을 때 pool이 말라붙는다.
`POOL=50` 이라 적어 놓고 실제로는 `문서 수 × 2` 개밖에 모으지 못한다.

카카오 "2024년 매출액" 조사에서 이것이 정답을 잘라내는 것을 확인했다[^kk].
`corp_name + fiscal_year=2024 + report_type=annual` 로 좁히면 후보 문서가 4개뿐이라
pool 최대치가 8이 되고, 정답인 「연결 포괄손익계산서」 표 본문 청크가 **RRF 3위
였는데도** 같은 문서의 다른 조각 둘(별도 포괄손익계산서 · 표 꼬리)에 밀려 버려졌다.

```python
n_docs  = 후보에 들어 있는 문서 수
per_doc = max(per_doc, min(pool // n_docs, pool // 2))
```

문서가 25개 이상이면 계산값이 2 이하라 **기존 동작과 완전히 같다.**
`pool//2` 상한으로 한 문서가 pool을 독점하지 못하게 막는다.
회사+연도로 좁히는 실제 질의는 후보 문서가 6~8개라 이 경로가 거의 항상 걸린다[^s47].

### 3.3 절 제목 가중(`w_section`)은 채택하지 않았다

절 제목을 점수에 섞으면 좋아질 것 같아 측정했으나 근거가 나오지 않았다[^ws].

| `w_section` | recall@5 | recall@20 |
|---|---|---|
| **0.0 (채택)** | **0.361** | 0.722 |
| 0.3 | 0.306 | 0.778 |
| 0.5 | 0.361 | — |
| 1.0 | 0.278 | — |

`0.3` 에서 recall@20만 오르고 recall@5는 떨어진다 — 위쪽 순위를 흔들면서 아래만
채운 것이라 쓸모가 없다. 기대와 달리 짧은 질의(2어절)에서 더 나빴다
(recall@20 0.500→0.333). 재무제표 절에서 절 제목이 문서마다 거의 같은 문자열이라
변별력이 아니라 잡음으로 들어간 것으로 본다.
표본이 18문항이라 **"확실히 나쁘다"까지는 말하지 않고 "좋아진다는 근거가 없다"**
까지만 말한다. 기본값 0을 유지했고 측정 기록은 코드 주석에 남겼다.

### 3.4 검색 성능

골든셋 18문항[^ge] (필터는 `corp_name` 뿐 — 후보가 2,628~12,552청크인 조건):

| 지표 | @1 | @5 | @10 | @20 | @50 |
|---|---|---|---|---|---|
| recall (`per_doc=2`) | 0.056 | 0.361 | 0.528 | 0.639 | 0.639 |
| recall (`per_doc=50`) | 0.056 | 0.361 | 0.528 | 0.722 | 0.833 |

> **이 숫자를 그대로 Agent 성능으로 읽으면 안 된다.** 골든셋 문항은 어느 문서인지
> 특정하지 않아 연도·접수일 필터가 전부 비어 있다. 실제 Agent는 질문에서 회사와
> 회계연도를 뽑아 필터로 넣으므로 후보가 1/3~1/10로 줄어든다.
> 또 라벨 19건 중 7건이 `found_by_grep`(검색으로 못 찾아 원문 grep으로 찾은 것)이라
> 분모 자체가 어려운 쪽으로 치우쳐 있다.

지연[^h] (GPU 없는 운영 서버 기준):

| | 값 |
|---|---|
| 첫 질의 | 4.4초 (워밍업) |
| 이후 | 100~210ms (GPU 70~80ms) |
| RAM | 로드 후 2.42GB → 검색 후 4.35GB |
| 병목 | 질의 임베딩 81ms · BM25 6ms. 후보가 190배 늘어도 159ms |

## 4. 에이전트

### 4.1 질문 재작성

원문 질문을 그대로 검색에 쓰면 "요약해줘" 같은 요청 동사가 질의어에 섞인다.
LLM 한 번으로 **회사 · 회계연도 · 하위 질문 · 공시유형**을 구조화해 뽑는다.

이 단계에서 배운 것은 **프롬프트만으로는 막히지 않는다**는 것이다.
`doc_groups` 를 내용으로 추정하지 말라고 규칙·예시·반례로 세 번 조였는데도
두 번 다 `["periodic"]` 이 나왔다[^s37]. 결국 코드 가드
(`rewrite._filter_doc_groups` — 질문 원문에 유형 낱말이 있을 때만 남긴다)를 넣었다.
같은 이유로 응답 형식 규칙도 프롬프트가 아니라 코드에서 정한다.

### 4.2 도구 5종

| 도구 | 하는 일 |
|---|---|
| `search_disclosure` | 공시 원문에서 근거 조각을 찾는다. 거의 모든 질문의 첫 단계 |
| `list_disclosures` | 어떤 공시를 몇 건 냈는지. **내용은 주지 않는다** |
| `calculate` | ast 화이트리스트 산술. 증감률·비중·차액·배수는 반드시 이걸 쓴다 |
| `get_progress_table` | 최신 정기보고서의 「공시내용 진행 및 변경사항」 표 |
| `resolve_company` | 회사 이름·약칭·별칭 → 정식 회사명·종목코드 |

**모든 도구는 어떤 입력에도 예외를 던지지 않고 `{"status": ...}` JSON을 반환한다.**
평가 중 예외가 나면 그 문항은 0점이기 때문이다.

호출 한도 6회(`MAX_TOOL_CALLS`), 소프트 데드라인 200초(`loop.DEADLINE`).

도구 결과에 실은 안내가 시스템 프롬프트보다 강하다는 것도 실측으로 확인했다.
`list_disclosures` 결과에 "이건 내용이 아니다"를 한 줄 넣자 후속
`search_disclosure` 호출이 **2회 → 14회**로 늘었다[^h]. 도구 결과가 12,000자씩
쌓이면 시스템 프롬프트는 멀어진다 — 고칠 지점 바로 옆에서 말해야 먹힌다.

### 4.3 최종 답변 검문 8종

최종 답변을 내려는 시점에 코드가 답변을 검사하고, 걸리면 **한 턴만** 되돌린다.
`elif` 사슬이라 **하나만** 걸리고, 문항당 **한 번**만 발동한다.
남은 시간이 `AUDIT_MARGIN`(20초) 미만이면 건너뛴다.

| 판정 순서 | 검문 | 무엇을 잡나 | 상태 |
|---|---|---|---|
| 1 | 검문 1 `calc` | 비율·배수를 답하면서 `calculate` 0회 | 사용 |
| 2 | 검문 6 `compare` | 여러 값의 크기를 비교하면서 `calculate` 미사용 | 사용 |
| 3 | 검문 8 `unsourced_num` | 답변의 수치가 검색 결과·질문·계산 어디에도 없음 | 사용 |
| 4 | 검문 7 `subq` | 하위 질문 수보다 본문 검색이 적음 | **비활성**(4.5절) |
| 5 | 검문 3 `no_search` | 어떤 공시도 조회하지 않고 거절 | 사용 |
| 6 | 검문 4 `all_bad` | 부른 도구가 전부 빗나갔는데 그대로 거절 | 사용 |
| 7 | 검문 5 `announced` | 도구를 부르겠다고 말만 하고 끝냄 | 사용 |

검문 2는 별도 분기가 아니라 **거절 표현 판정**(`_AUDIT_REFUSE` = "확인되지 않"·
"확인할 수 없")이며 검문 3·4가 공유한다. 검문 1은 지시를 좁혀 **문서에 그대로
있는 비율은 걸지 않는다** — 그러지 않으면 공시에서 베낀 '매출액대비 3.06%' 같은
값에도 걸려 거의 모든 답변이 검문을 타고 호출이 하나씩 더 붙는다.

검문에는 두 개의 안전장치가 붙어 있다.

- **브레이크(`AUDIT_TAIL`)** — 검문 조건이 전부 "더 하라"(계산해라·더 검색해라)
  방향이고 답변 직전에 오기 때문에, e2e_v6에서 검문 발동 문항의 **환각 5건**이
  나왔다. "근거 없으면 확인되지 않음으로, 값을 만들어내지 마라"를 붙여 잡았다[^s44].
- **되돌림 방어(`audit_degraded`)** — 검문을 받은 모델이 답을 고치는 대신
  검문 지시를 답변 본문으로 되읊는 일이 있다. 검문 전 답변을 보관해 두고
  나빠졌으면 되돌린다. e2e_v6에서 **11건** 발동했다[^v6].

### 4.4 후처리

프롬프트로 두 번 샌 자리를 코드로 막았다.

- `strip_placeholders` — 자리표시자(ㅇㅇ전자·△△지주·XXXXXX) 문단 제거
- `strip_leadin` — 서두 군더더기 제거 (v4 15건 → v5 **0건**)[^v5]
- `strip_prose_geun` — 근거 중복 제거 (v4 3건 → v5 **0건**)[^v5]
- `strip_correction_contrast` — 정정 전 값과 대조하는 문장을 **문장 단위로** 제거.
  질문이 "정정 전"을 물었으면 예외, 지워서 값이 사라지면 원문 유지[^s46]

### 4.5 실패한 시도 — 검문 7을 껐다

"하위 질문 수보다 검색이 적으면 더 검색시킨다"는 규칙이 e2e_v6에서
**40문항 중 19건** 발동했다[^v6]. 대부분 "하위 2개 / 검색 1회"인데, 하위 질문
둘을 한 번의 검색으로 답할 수 있는 경우가 많았다. LLM 호출이 148→170회,
비용이 1,239→1,681원으로 늘었다. 임계를 조정하는 대신 **비활성화**했다
(`SUBQ_AUDIT_ENABLED=False`). 코드와 테스트는 남겨 뒀다.

## 5. 서비스

### 5.1 API 규격

`GET /answer?question_id=&question=` → **200 + 5필드 문자열 JSON**,
`GET /health` → 준비 전 503 / 준비 후 200. 자세한 것은 [docs/API.md](API.md).

**준비된 뒤에는 무슨 일이 있어도 200과 규격 JSON을 돌려준다.** 5xx를 뱉으면
재시도 2회를 낭비하고 결국 미응답 처리된다. 내부 예외·타임아웃·빈 질문 전부
5필드로 채워 나간다.

### 5.2 시간 층위

```
주최측 300초 > API 하드 240초(HARD_DEADLINE) > 에이전트 소프트 200초(loop.DEADLINE)
                                                ↳ 검문 여유 20초(AUDIT_MARGIN)
```

하드 데드라인은 답변 생성을 워커 스레드에서 돌리고 `join(240)` 하는 방식이다.
loop가 비정상적으로 멈췄을 때(네트워크 행) 주최측 타임아웃 전에 폴백이라도
보내기 위한 마지막 방어선이다. 타임아웃에 딱 맞추면 답변을 만드는 도중에 상대가
먼저 끊는다.

### 5.3 HyperCLOVA X 호출

실측으로 데인 것들[^h]:

- `function.arguments` 가 JSON 문자열이 아니라 **객체**로 온다. `json.loads()` 를
  걸면 터진다
- 도구 호출은 `maxTokens >= 1024` 필수
- **429가 잦다.** 백오프는 최소 6초부터, 연속 호출 사이 20~30초.
  누적 429 재시도 80회 · 대기 840초[^tk]
- HTTP 400 `40009 Unsupported function` 이 산발적으로 난다(40문항당 1건, 2회 관측).
  **첫 호출에서 나면 그 문항을 통째로 잃는다** — 도구 0회, 무근거 답변이 된다
- 단가는 입력 1,000토큰 1.25원 · **출력 1,000토큰 5원**. 출력이 4배 비싸므로
  총 토큰 하나로 환산하면 최대 4배 틀린다. 입력·출력을 분리해 회계한다

### 5.4 배포

systemd(`dis044.service`)가 80 포트로 관리한다. `scripts/deploy.sh` 가
코드를 tar 하나로 묶어 scp → 원격에서 풀기 → `systemctl restart dis044` →
`is-active` + `/health` 200을 최대 120초 폴링 → 실패 시 `journalctl` 출력까지
한 번에 한다. 인덱스·모델 캐시·`.env` 는 서버 것을 그대로 둔다.

GPU 없는 서버에서 CPU로 돈다. 판단은 `gpu_guard.cuda_ok()` 한 곳에서만 한다
(`FORCE_CPU=1` 로 개발 PC에서 서버를 재현할 수 있고, 검색 결과가 서버와
완전히 일치하는 것을 확인했다[^h]).

**운영 실측(2026-09-06 09:44)**: `/health` → `{"status":"ok","warm_seconds":8.7,
"served":11,"uptime":116737.9}` — 무중단 **32.4시간**. 실질의 8.9초 · 12,511 bytes.

## 7. 한계와 개선 방향

각 항목의 **근거 파일과 현재 상태**를 함께 적는다.
"채택하지 않음"은 남은 기간에 회귀 검증을 할 수 없어 손대지 않기로 한 것이다.

### 7.1 문서당 상한으로 인한 pool 축소 — **채택(수정 완료)**

`PER_DOC=2` 고정이 좁은 필터에서 pool을 마르게 하고, RRF 3위인 정답 청크를
같은 문서의 다른 조각으로 밀어냈다. 카카오 "2024년 매출액" 전량 조사에서
확인했다[^kk].

- **조치**: `per_doc = max(per_doc, min(pool//n_docs, pool//2))`[^s47]
- **검증**: 골든셋 18문항 recall@5 0.361 · @20 0.639 **수정 전후 동일**
  (문항별 순위도 전부 같음 — 골든셋은 필터가 회사뿐이라 후보 문서가 24~122개라
  이 변경이 걸리지 않는 표본이다) · 회귀 7문항 **7/7**(직전 6/7, KB금융 개선)
- **남은 한계**: e2e 40문항 재실행을 하지 못했다. 40문항 규모에서의 효과는
  측정되지 않았다

### 7.2 「매출액」 ↔ 「영업수익」 표기 차이 — **부분 채택(planner 규칙만)**

재무제표에서 매출을 「영업수익」으로 적는 회사가 있다. 카카오 2024 사업보고서
정정본 911청크에서 **영업수익 184회 vs 매출액 27회**이고, 「매출액」은 II. 사업의
내용과 IV. 경영진단에만 있다. 그래서 `매출액` 으로만 검색하면 연결 포괄손익계산서
청크의 **BM25 점수가 정확히 0**이 된다[^kk].

- **조치**: planner에 "매출을 검색할 때는 매출액과 영업수익을 함께 넣는다" 한 줄.
  검색기는 건드리지 않았다[^s47]
- **검증(23개사 A/B, LLM 0회)**: 좋아짐 10 · 나빠짐 3 · 동일 10.
  순증이지만 공짜가 아니다 — "영업수익"이 주석의 「고객과의 계약에서 생기는 수익」
  표를 끌어올려, 표기가 원래 「매출액」인 회사(기아 등)에서는 「매출 및 수주상황」이
  top-5 밖으로 밀린다
- **남은 한계**: 회귀 7문항에서 모델이 실제로 "영업수익"을 쓰지는 않았다.
  프롬프트 한 줄이 행동을 바꾸는지는 아직 확인되지 않았다.
  검색기 차원의 질의 확장은 **잔여 기간 내 회귀 검증이 불가해 채택하지 않았다**

### 7.3 계열 식별자로 계약 정정을 추적할 수 없다 — **채택하지 않음**

HD현대일렉트릭 고압차단기 계약에서 최초 공시(583억)를 찾고 정정공시(644억)를
못 보는 문제가 있었다. `series_code` 로 이으려 했으나 실측 결과 **그 회사의
「단일판매ㆍ공급계약체결」 전부가 계열 하나(계열 15)로 묶여** 있었다[^sr].

```
20240130800387 (최초, 583억) -> 계열 15 -> 계열 최신 20260106800025
20250225800764 (정정, 644억) -> 계열 15 -> 계열 최신 20260106800025
계열 최신 20260106800025 = 전혀 다른 계약 (983억 · 2028-11-09)
```

정기보고서는 제목에 기간이 들어 있어(「사업보고서 (2024.12)」) 계열이 성립하지만,
이벤트 공시는 같은 제목으로 매번 다른 사건을 낸다(삼성E&A는 이 제목으로 87건).
**고치려면 계열이 아니라 계약명으로 짝지어야 한다.**

- 우회책으로 `get_progress_table`(정기보고서의 「공시내용 진행 및 변경사항」 표)을
  넣었고 회귀 7번이 PASS로 바뀌었다. 다만 도구 설명·planner 강조로는
  최근 7표본 중 3회만 PASS — **확률을 움직일 뿐 결정적이지 않다**[^s45]
- 계약명 매칭 파이프라인은 **잔여 기간 내 회귀 검증이 불가해 채택하지 않았다**

### 7.4 하위 질문 분할 파이프라인 — **채택하지 않음**

"하위 질문마다 검색을 한 번씩 돌린다"는 접근은 닫힌 질문(단일 수치)에서는
동작하지만 개방형 질문에는 적용할 수 없었다. 검문 7의 19/40 과다 발동이
그 증거다(4.5절) — 하위 질문 둘이 한 번의 검색으로 답해지는 경우가 대부분이었고,
비용만 36% 늘었다.

- 하위 질문별 검색·병합 파이프라인은 **잔여 기간 내 회귀 검증이 불가해
  채택하지 않았다.** 검문 7 코드와 테스트는 되살릴 수 있게 남겨 뒀다

### 7.5 그 밖에 남긴 것

| 항목 | 상태 |
|---|---|
| **산문에 묻힌 답** (삼성생명·삼성화재) — 긴 산문 청크를 재분할해야 잡힌다 | 재임베딩이 필요해 대회 기간 내 불가 |
